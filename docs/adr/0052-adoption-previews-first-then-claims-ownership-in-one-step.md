# Adoption previews first, then claims ownership in one step

The **adoption preflight** reads the container, not the manifest. Only the container knows which host directories and named volumes it mounts, which of them it may write, which image it runs, and which label its manager left on it, so the hub reads its storage inventory from the Docker daemon's own view and records it as it found it. A manifest that references a path is not permission to own that path, and a read-only mount two instances share is recorded as read-only rather than as something a later deletion may take. The preflight opens nothing, writes nothing and registers nothing, so an operator can run it as often as they like, and the handoff runs it again before it has any effect.

An adopted instance's **hub instance ID** is derived from the host directory it owns rather than minted fresh. The id the preview proposes is therefore the id the handoff uses, a second spelling of the same path is the same instance instead of a second one, and a handoff that was interrupted writes over its own unfinished record rather than opening another. Duplicate adoption is then exactly "this hub already manages that id", and storage that overlaps another record is reported against the instance that owns it, separating a record the hub runs from one it only retains.

The hub cannot verify that Compose has let go, and it will not pretend to. Two findings turn on an explicit answer from the operator instead: one that the previous manager no longer recreates the container, and one that a runtime which cannot drain may be interrupted. The preflight explains the Compose and old-updater steps, the expected downtime and how the webhook URL survives; the operator does those steps and says so in the command, and the hub records the answer with the operation. The hub never substitutes the interrupting stop for a graceful handoff. A runtime that reports the drain capability drains, and one that does not goes down only under the acknowledgement, in a step named for what it is.

Ownership moves in one recorded step, after the previous runtime is down and before its container is removed. Until that step the instance is not the hub's, so an interrupted handoff is reported as "the previous manager still holds this container"; after it the instance is the hub's with a container that may be missing, which is the case [ADR 0051](0051-recovery-reports-what-it-finds-and-recreation-is-explicit.md) already answers with an explicit recreation. Neither state is a guess about who owns the data. The hub writes its own **control token** beside the instance as part of the handoff, because the container it creates reads that file once, when it is created.

A container's name is its runtime id. The container runtime no longer prefixes the id it is given, and it mounts exactly the **storage inventory** the hub recorded instead of recomputing the instance's paths, because an adopted container keeps the name and the storage its previous manager gave it. The hub, which already maps its own directory onto the Docker host, stays the one place that decides what a created instance owns.

Adoption travels over the hub's contract as a preview method and a lifecycle operation rather than as a local command. The running hub holds an exclusive lock on its directory, so a second process cannot open the registry to adopt anything while the hub is up. Attaching the existing container to the hub's private network stays an operator step that the preflight names, because the hub does not touch a container whose manager has not let go of it yet.
