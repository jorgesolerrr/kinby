# Recovery reports what it finds, and recreation is explicit

A hub that opens its directory reconciles each managed instance once, before it serves anything. It reads the instance registry and the containers labeled with its own hub id, then acts on exactly one case: a container that exists, whose instance is recorded as intended running, and whose last lifecycle operation succeeded, is started again. Everything else is reported and left alone — a missing container, a container whose instance the registry does not know, an unhealthy instance, an unreachable container runtime, a storage source two instances claim, and a container still running against a recorded intent to stop.

Recovery never repeats a lifecycle operation that failed, whether it failed on its own or because the previous process died mid-effect. [ADR 0050](0050-a-stop-drains-the-instance-then-takes-the-container-down.md) already settled that the new process fails what the old one left unfinished and the client asks for another; retrying inside recovery would race that client and would drain or replace an instance nobody asked about at that moment. Recovery does write one thing it did not do itself: when an unprepared instance already has its container, creation reached its last effect and only the outcome was lost, so recovery records that outcome instead of creating a second container. That is the difference we hold onto — recovery may record what it observes, and may restore intended state, but it starts no create, no stop, and no replacement. Every lifecycle mutation added later has to extend this pass with the stage it can be interrupted in, and with what the hub should report when it finds that stage half-done.

Recreation is therefore its own authorized operation, and the only one that brings a missing container back or applies replaced **instance secrets**. It revalidates the retained configuration, the recorded image artifact, and storage ownership before any effect; it refuses while another operation is in flight for that instance; and for a container that still exists it takes the established drain-then-stop path from ADR 0050 before removing it. It reuses the recorded image rather than resolving a revision, so recreating is never an update, and it leaves the instance's intended state, named volumes, bind directory, and secret file untouched. An interruption between the removal and the create leaves a failed operation a client can read and a missing container the next recreation fixes.

Replacing secrets is a lifecycle operation of its own for the same reason: the values live in a file beside the instance, the container that reads them already exists, and the hub will not pretend that a write changed a running container's environment. The write merges into the existing file through a staging file and one rename, so a failure leaves the previous secrets whole rather than half-replaced, and neither the registry, the operation record, nor a read response ever carries a value back.

Decision agreed during [Recover lifecycle state and explicitly recreate containers](https://github.com/jorgesolerrr/kinby/issues/240), under [ADR 0037](0037-the-hub-owns-lifecycle-state-in-sqlite.md) and [ADR 0050](0050-a-stop-drains-the-instance-then-takes-the-container-down.md).
