# Memory is one facade over feeds proven in order

Ticket #8 chose one internal facade — recall, remember, forget — that core calls directly and the model reaches only through core memory tools, over per-feed APIs scattered through the runtime, so a server can later wrap the same seam without new machinery; no contract methods ship in v1. Feeds are built in order — profile file, then the light knowledge graph, then a RAG index over the transcript store — and each must pass expected-behavior checks, measured as (answer correctness, memory tokens spent) against a stuff-the-whole-transcript baseline, before the next starts; numeric thresholds belong to eval design (#10). The graph starts as markdown nodes in `memory/graph/` — episodes (a task's distillation, including the trace of tools used and the path taken, so a later turn on the same problem can reuse or improve it) and facts (atomic, timestamped) — walked by two deterministic tools: search over frontmatter descriptions and subjects with date bounds, newest first, and open for a node's body. A vector or graph database was rejected for v1 because the temporal questions the graph must answer (what happened on day X; when did I last touch Y; what did we decide about Y and is it current) need dates, subjects, and recency, not embeddings; whether a decision is current resolves as latest-fact-wins per subject, with no supersedes edges. Forget writes a tombstone the ingestion pipeline respects, because the graph is derived from the transcript store and deletion alone would resurrect a fact on re-ingestion; the transcript store is never rewritten. Nodes are human-legible and live in `memory/`, not `.state/`, because a user correcting their agent's memory is the point; only recomputable indexes go to `.state/`.
