# Gate policy is per-tool rules under mode presets

Ticket #7 chose per-tool allow/ask/deny rules with four named presets (read-only, ask, auto, full-access) over T3-style fixed modes, because fixed modes cannot classify plugin tools their vocabulary never heard of; a preset is just a named bundle of per-tool rules that `permissions.toml` overrides tool by tool. The tool `write` flag stays the author's one-bit declaration (ADR 0010); policy belongs to the instance: `permissions.toml` sets the default mode and the ceiling, and a thread pins its own mode through `thread.mode.set`, never above the ceiling. Bash asks in every mode below full-access because it can do everything the path-bounded file tools can. The bash denylist is regex patterns enforced even in full-access, yet it is a tripwire, not a wall: patterns are bypassable by construction, and isolation comes from the container (hard wall) and the gate's ask (soft wall). The gate assumes no revert mechanism exists; per-turn checkpoints may later justify loosening a default, never the reverse.
