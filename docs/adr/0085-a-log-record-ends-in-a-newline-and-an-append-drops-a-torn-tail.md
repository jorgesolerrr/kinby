# A log record ends in a newline, and an append drops a torn tail

`events.jsonl`, `threads.jsonl` and `config-changes.jsonl` count a record only once its newline is written. A container killed mid-append or a full disk leaves a torn tail, the bytes after the last newline. Reads skip it without parsing it. A read stops at the last newline the file had when it was opened. A newline, once written, is never removed and nothing before it changes, so a reader that holds no lock streams the log line by line and never joins a tail to the record that replaced it. Before every append the writer truncates the file to its last newline and logs the dropped fragment, so the next record starts on a line of its own and the sequences continue from the last whole event. An unparseable line before the last one still fails the read, because that is corruption and not a torn tail.

Truncating is safe only for the one process that writes the instance, as ADR 0006 requires. Inside it, configuration writes run on worker threads under separate locks, so every append takes one lock in the writing process. A second writer could have its record cut while still writing it, so the CLI's thread commands that append take the runtime lock and refuse to run beside a live instance.
