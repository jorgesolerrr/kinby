# An update prepares the candidate, then replaces the container

An **instance update** names one revision and nothing else. The instance's recorded **package** selection travels into the shared image-preparation path unchanged, because moving an instance to another package version is its own operation, with the configuration rules [ADR 0039](0039-package-updates-preserve-instance-configuration.md) already settled. Before anything moves, the update revalidates the retained configuration and storage ownership, prepares the candidate through the path creation uses, and checks that the prepared image carries the selection it asked for. All of that leaves the running container alone. A revision that will not resolve, an image that will not build, and a candidate missing the instance's package each end as a failed operation with the instance still serving from its selected image.

The replacement itself is the drain-then-stop path of [ADR 0050](0050-a-stop-drains-the-instance-then-takes-the-container-down.md) followed by the create of [ADR 0051](0051-recovery-reports-what-it-finds-and-recreation-is-explicit.md). Accepted work finishes, the container goes away, its storage stays, and the per-instance lock serializes the operation against every other lifecycle mutation. The hub records the new image as this instance's selection when the container is created from it, and not before, so the record names the image the container actually has. The previous identity stays readable on the operation's `replace` step and its artifact row stays in the registry, which is what an explicit recovery needs.

An update does not change the instance's intended state. A stopped instance is updated and left stopped. A running instance is started again, and the update reports success only once the instance answers its own lifecycle endpoint, because a container that runs is not an instance that booted. When it never answers, the operation fails and stays failed. Nothing rolls back. The replacement may already have changed the data it now owns, and starting an older image against changed data is worse than an instance the user has to look at.

Recovery therefore reads one more stage. An interrupted preparation leaves a running container, and recovery reports it as running. An interrupted replacement leaves no container at all, and recovery reports that as missing and names the failed operation, so recreating from the recorded image is a choice rather than an accident. A replacement that created its container before the hub died leaves a container against a failed operation, which [ADR 0051](0051-recovery-reports-what-it-finds-and-recreation-is-explicit.md) already refuses to start under a stale intent to run.

Decision agreed during [Update from a prepared immutable image](https://github.com/jorgesolerrr/kinby/issues/241), under [ADR 0035](0035-hub-updates-select-an-immutable-image.md) and [ADR 0038](0038-image-artifacts-come-from-restricted-source-snapshots.md).
