# Removal retains the record, and restoration is explicit

An **instance removal** takes the container down the drain-then-stop path from [ADR 0050](0050-a-stop-drains-the-instance-then-takes-the-container-down.md) and removes only that container. The storage rows stay in the registry, so the storage stays reserved against adoption, creation, and replacement for other instances, and the hub deletes no directory or volume. "Removed" is a third intended state beside running and stopped, not a new column. The hub writes it once the container is gone. A removal interrupted before that point leaves an instance the user can still see and remove again, and recovery reports it as incomplete. A removal interrupted after the container went has already reached its last effect, so recovery records it as removed, the same way [ADR 0051](0051-recovery-reports-what-it-finds-and-recreation-is-explicit.md) records a create that reached its container. A start accepted while that removal drains is recorded later and leaves the container where it is. Recovery still finishes the removal.

An **instance restoration** runs only when a user asks for it. It revalidates the retained configuration and checks that the directory still holds the same manifest id. It also checks storage ownership against active and removed records, then asks the container runtime whether the selected image and every named volume still exist. The hub needs that last check because Docker creates a new, empty volume when a mount names one that is missing, and that empty volume would take the place of the user's workspace or credentials without an error. A missing image fails the restoration because choosing another image would be an update. Restoration leaves the instance stopped, because removal stopped it, and a start is a separate request. Recovery counts a container under a removed record as the restoration's only when this hub labeled it, and then records the instance as stopped. It reports any other container and changes nothing.

A pending removal drain registers where a stop's does, so a force stop escalates it inside the same operation.

Decision agreed during [Remove and restore instances while retaining data](https://github.com/jorgesolerrr/kinby/issues/243), under [ADR 0050](0050-a-stop-drains-the-instance-then-takes-the-container-down.md) and [ADR 0051](0051-recovery-reports-what-it-finds-and-recreation-is-explicit.md).
