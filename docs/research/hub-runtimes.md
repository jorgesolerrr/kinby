# Container runtimes for the hub: Docker Engine API and the Kubernetes mapping

Wayfinder ticket: jorgesolerrr/kinby #212, part of the map "kinby next: hub, packages, web app, usage map" (#211). Date: 2026-09-11.
Question: which API the hub uses to create, start, stop, remove, inspect and read logs of instance containers on Docker; how the same operations map to Kubernetes; what shape a `Runtime` Protocol needs so both implementations fit without Docker leaking into it; and whether the hub's own state can stay in SQLite under Kubernetes or needs Postgres.

Sources: the Docker Engine API reference and its OpenAPI spec (v1.56), the Docker SDK for Python docs and source (docker 7.2.0), the Docker security, networking, labels and Compose docs, the Kubernetes concept pages for Deployment, StatefulSet, PersistentVolume, Secret, Service, Ingress, Pod lifecycle, owners and dependents, RBAC and recommended labels, the kubernetes-client/python README and generated API docs (kubernetes 36.0.3), PyPI metadata, and the SQLite pages on when to use it, locking and WAL. On top of the reading, docker 7.2.0 and kubernetes 36.0.3 were installed into a scratch venv on CPython 3.14.2 and a probe script ran every Runtime verb against the local daemon (Docker 27.0.3, API 1.46). Probe results are marked "probe" below.

## Short answer

Use the Docker SDK for Python (`docker` 7.2.0) over the daemon socket, with `docker.from_env()`. It is the Engine API with the plumbing already done: socket adapters for Unix and Windows, API version negotiation, and the demultiplexing of the log stream. The six verbs map one to one onto `containers.create`, `Container.start`, `Container.stop(timeout=)`, `Container.remove`, `Container.reload()` plus `attrs["State"]`, and `Container.logs(...)`. Labels go on at create and are the hub's only registry key on the daemon side; the instance directory is a bind mount at `/instance`; secrets come from the instance `.env` parsed with `dotenv_values` (python-dotenv is already a dependency) and passed as `environment`; the Caddy network is joined at create with `network=`. The SDK is synchronous, so the hub wraps calls in `asyncio.to_thread`. Probe: all of this worked on Python 3.14 in one run.

On Kubernetes each instance is one Deployment with `replicas: 1` and `strategy: Recreate`, one ReadWriteOnce PersistentVolumeClaim at `/instance`, one Opaque Secret consumed with `envFrom`, one ClusterIP Service, and optionally one Ingress rule. Create makes the objects with `replicas: 0`; start and stop patch the scale; remove deletes the Deployment (cascading to ReplicaSet and Pods) and, when asked, the PVC; status reads the Pod phase and container state; logs come from `read_namespaced_pod_log`. The client is `kubernetes` 36.0.3, which ships an asyncio variant under `kubernetes.aio`.

The Protocol that fits both is small: an `InstanceSpec` value (id, image, command, env, port, files to seed) in, an opaque instance id for every other verb, a `RuntimeStatus` value out, and an async iterator of bytes for logs. Two things must not be in it: host paths and container ids. Both stay inside the Docker implementation. One verb the ticket does not list is needed: `exec`, because the Codex device-code login and the "is a coding client running" check both go through `docker compose exec` and `docker compose top` today.

SQLite stays. The hub is one process with one writer, which is SQLite's own recommended case. Under Kubernetes the hub runs like an instance: a single-replica Recreate Deployment over a ReadWriteOnce claim, where SQLite's locking and WAL work because the volume is a local filesystem on one node. The one concrete way to break it is an NFS-backed ReadWriteMany class, which SQLite's own docs rule out, and the instances already carry the same constraint through their `.state/checkpoints.sqlite` (ADR 0015). Postgres would buy nothing the single-user hub uses.

## How instances run today

`compose.yaml` runs one service per directory under `instances/`: it builds the root image, mounts `./instances/coder` at `/instance`, reads secrets from `instances/coder/.env`, adds two named volumes (`coder-workspace` at `/instance/workspace`, `coder-codex` at `/root/.codex`), publishes `127.0.0.1:8787`, runs `serve` with a `curl /health` healthcheck and `restart: unless-stopped`. `compose.public.yaml` adds Caddy with a Caddyfile that hardcodes `reverse_proxy coder:8787`; Caddy reaches the coder by service name on the Compose default network. `docker/entrypoint.sh` prepares the mounted instance on every start (git safe directory, profile copy, workspace clone, Codex config) and then `exec kinby "$@"`. `docker/update.sh` runs `docker compose up --build --detach --remove-orphans` from cron after checking `docker compose top coder` for a running `codex` or `claude` process. `docs/container.md` and ADR 0030 record all of this.

Three facts from that setup shape the mapping:

- The instance directory is a bind mount and the workspace is a named volume for one reason, written in the compose file: a clone on a Windows or macOS bind mount "crosses the host bind mount on every file access". On a Linux box, and on a Kubernetes volume, that reason is gone.
- Compose marks its containers with `com.docker.compose.project` and `com.docker.compose.service` labels (probe: `My-agent-coder-1 My-agent coder` on this machine), and `--remove-orphans` means "Remove containers for services not defined in the Compose file" (https://docs.docker.com/reference/cli/docker/compose/up/). A hub container that carries no Compose labels is not an orphan of any project, so the cron update leaves it alone. The hub must not imitate Compose labels.
- Two operations already reach inside the container: `docker compose exec coder codex login --device-auth` and the `docker compose top` check. They are the reason for the `exec` verb below.

## Docker: which API and which library

The Engine API is a REST API. "When using `curl` directly, specify the version as the first part of the URL. For instance, if the endpoint is `/containers/` you can use `/v1.56/containers/`" and "The Docker Engine API server and client support API-version negotiation" (https://docs.docker.com/reference/api/engine/). The current version is v1.56; "API versions before v1.40 are deprecated and no longer supported by current versions of the Docker Engine and CLI" (https://docs.docker.com/reference/api/engine/version-history/). The daemon speaks it on `/var/run/docker.sock`, which is also the security boundary: "This daemon requires `root` privileges unless you opt-in to Rootless mode", "only trusted users should be allowed to control your Docker daemon", and the socket exists so administrators "use traditional Unix permission checks to limit access to the control socket" (https://docs.docker.com/engine/security/). A hub that mounts the socket has root on the box. That is the same trust the box already places in whoever runs `docker compose`, but it is worth writing into the hub's spec.

The SDK, `docker` 7.2.0 (2026-07-09, Apache-2.0, `Requires-Python >=3.8`, depends on `requests>=2.26.0`, `urllib3>=1.26.0` and `pywin32` on Windows; https://pypi.org/project/docker/), is "A Python library for the Docker Engine API. It lets you do anything the `docker` command does, but from within Python apps". `from_env()` reads `DOCKER_HOST`, `DOCKER_TLS_VERIFY` and `DOCKER_CERT_PATH`; 7.2.0 added "`docker.from_env()` now honors the active Docker CLI context when `DOCKER_HOST` is not set" (https://docker-py.readthedocs.io/en/stable/change-log.html). Constants: `DEFAULT_UNIX_SOCKET = "http+unix:///var/run/docker.sock"`, `DEFAULT_NPIPE = "npipe:////./pipe/docker_engine"`, `DEFAULT_DOCKER_API_VERSION = "1.45"`, `MINIMUM_DOCKER_API_VERSION = "1.24"`, `DEFAULT_TIMEOUT_SECONDS = 60` (https://github.com/docker/docker-py/blob/main/docker/constants.py). `from_env()` negotiates the version; probe: `client.api._version` came back `1.46` against Docker 27.0.3, whose own minimum is 1.24.

Three things the SDK does that a raw socket client would have to redo:

- Transport. `APIClient` subclasses `requests.Session` and mounts a `UnixHTTPAdapter` for `unix://` and a named-pipe adapter for `npipe://` (https://github.com/docker/docker-py/blob/main/docker/api/client.py). The hub works on the Linux box and on a Windows dev machine with the same call.
- The log stream. Without a TTY the logs endpoint returns the attach format: an 8-byte header `[STREAM_TYPE, 0, 0, 0, SIZE1, SIZE2, SIZE3, SIZE4]` where type 1 is stdout and 2 is stderr, then that many payload bytes, repeated (https://docs.docker.com/reference/api/engine/version/v1.56/, ContainerAttach). The SDK's `_multiplexed_response_stream_helper` and `_get_result_tty` split that into frames. Probe: `logs(stdout=True, stderr=False)` and `logs(stdout=False, stderr=True)` returned the two streams separately.
- Types. `docker.types.Mount(target, source, type='volume', read_only=False, ..., subpath=None)` builds the `HostConfig.Mounts` entry (https://github.com/docker/docker-py/blob/main/docker/types/services.py); `RestartPolicy`, `Healthcheck` and `EndpointConfig` do the same for the rest of the create body.

The SDK is synchronous, and that is the one thing to design around. Every call blocks on `requests`; `logs(stream=True, follow=True)` returns a blocking generator. The hub runs on the asyncio loop `kinby serve` already owns, so the Docker implementation wraps each call in `asyncio.to_thread` and feeds the follow generator through a thread as well. The alternative, `aiodocker` 0.27.0 (aio-libs, aiohttp-based, Apache-2.0; https://pypi.org/project/aiodocker/), is async-native but covers fewer endpoints, has no typed helpers for mounts and endpoints, and lists no 3.14 classifier either. A thread per blocking call is cheaper than a second Docker client library, and the map settled on the SDK.

Python 3.14. The `docker` wheel's classifiers stop at 3.12 (PyPI metadata), but the package is pure Python over `requests`. Probe: installed with `uv pip install docker` on CPython 3.14.2 and ran the whole verb set. Nothing to work around.

Podman. `podman system service` exposes "a compatibility layer offering support for the Docker v1.40 API" on `unix:///run/podman/podman.sock` (rootful) or `unix://$XDG_RUNTIME_DIR/podman/podman.sock` (rootless), reachable by setting `DOCKER_HOST` (https://docs.podman.io/en/latest/markdown/podman-system-service.1.html). The SDK's minimum is 1.24, so a Podman box works with the same implementation and a `DOCKER_HOST`. Not a goal, but free.

## Verb by verb on Docker

All calls below are from https://docker-py.readthedocs.io/en/stable/containers.html unless another source is named. Every one of them ran in the probe.

**create.** `client.containers.create(image, command, name=..., labels=..., environment=..., mounts=[...], network=..., restart_policy=..., healthcheck=..., detach=True)`. "Create a container without starting it. Similar to `docker create`." Raises `docker.errors.ImageNotFound` and `APIError`. Per argument:

- `labels`: "A dictionary of name-value labels". Labels "are static for the lifetime of the object. To change these labels you must recreate the object", and third-party tools "should prefix each label key with the reverse DNS notation of a domain they own"; `com.docker.*`, `io.docker.*` and `org.dockerproject.*` are reserved (https://docs.docker.com/engine/manage-resources/labels/). kinby has no domain; a `kinby.` prefix (`kinby.hub=<hub id>`, `kinby.instance=<instance id>`) collides with nothing and reads as what it is. Probe: the labels came back on inspect under `Config.Labels` after create, stop, and restart.
- `environment`: "Environment variables to set inside the container, as a dictionary or a list of strings". The SDK has no `env_file` argument; that is a CLI and Compose feature. Its own `docker.utils.parse_env_file` is a bare `key=value` splitter that rejects any other line (https://github.com/docker/docker-py/blob/main/docker/utils/utils.py). python-dotenv, already a kinby dependency, is the better parser: `dotenv_values` "doesn't touch the environment, it just returns a `dict`", and it accepts quotes, comments and `export` lines (https://github.com/theskumar/python-dotenv). Probe: an `.env` with a comment, a quoted value and an `export` line parsed to the two expected keys, and the container printed the secret. `docker inspect` shows every value under `Config.Env`; that is true of Compose's `env_file` today as well, and it is one more reason the socket is a root-equivalent boundary.
- `mounts`: "More powerful alternative to `volumes`. Each item in the list is expected to be a `docker.types.Mount` object." `Mount(target="/instance", source=<host path>, type="bind")` reproduces the compose line; `Mount(target="/instance/workspace", source="kinby-<id>-workspace", type="volume")` reproduces the named volume. Mount types are `bind`, `volume`, `tmpfs`, `npipe`, `cluster`, `image` (v1.56 spec). One trap when the hub itself runs in a container: a bind `source` is a path on the host, not in the hub's filesystem. The Docker implementation therefore takes the host path of the instances directory as a setting, and the hub mounts that same directory at a known path of its own. With named volumes the trap disappears, at the cost of the hub having to mount each volume it wants to write into.
- `network`: "Name of the network this container will be connected to at creation time. You can connect to additional networks using `Network.connect`. Incompatible with `network_mode`." The source sets `host_config_kwargs['network_mode'] = network` and a `NetworkingConfig` for it (https://github.com/docker/docker-py/blob/main/docker/models/containers.py). On a user-defined network "containers can communicate with each other using container IP addresses or container names" (https://docs.docker.com/engine/network/), which is how Caddy will reach `kinby-<id>:8787`. The Compose network is named after the project, "Compose assigns the project name based on the name of the directory that contains the Compose file" (https://docs.docker.com/compose/how-tos/project-name/), so on the box under `/home/jorge/dev/kinby` it is `kinby_default`. The hub joins it by name; nothing in `compose.yaml` changes. If the hub is ever started before Compose, `networks.create` with the `external` pattern from https://docs.docker.com/compose/how-tos/networking/ inverts the ownership; either way the network name is one hub setting. Probe: `network=` at create put the container on the named network only.
- `restart_policy`: `{"Name": "unless-stopped"}`; the API enumerates `no`, `always`, `unless-stopped`, `on-failure` (v1.56 spec, RestartPolicy). `unless-stopped` matches Compose today and survives a daemon restart without resurrecting an instance the hub stopped. Probe: `HostConfig.RestartPolicy` came back as set.
- `healthcheck`: "The dict takes the following keys: test, interval, timeout, retries, start_period", the same `curl /health` test as the compose file.
- `ports`: not needed. Caddy reaches the instance over the network; nothing is published on the host. The `127.0.0.1:8787` publish in `compose.yaml` exists for the local `gh webhook forward` flow, which the hub does not need.

**start.** `container.start()`. "Similar to the `docker start` command, but doesn't support attach options." Probe: status went `created` to `running`; a second `start()` after a stop reused the same container, labels and mounts.

**stop.** `container.stop(timeout=N)`. "`timeout` (int): Timeout in seconds to wait for the container to stop before sending a `SIGKILL`. Default: 10". The API's `t` is "Number of seconds to wait before killing the container" (v1.56 spec, ContainerStop) and 304 means "container already stopped". `kinby serve` handles SIGTERM by setting its stop event and draining, so the timeout should cover a turn in flight; the coder's update script waits for a coding client to finish instead of interrupting it, and the hub inherits that rule. Probe: `stop(timeout=2)` on a process that ignores SIGTERM took 2.2 s and left exit code 137.

**remove.** `container.remove(v=True)`. "`v` (bool): Remove the volumes associated with the container"; the API says `v` removes "anonymous volumes" and `force` means "If the container is running, kill it before removing it"; removing a running container without `force` is a 409 (v1.56 spec, ContainerDelete). Named volumes and bind-mounted directories are never removed by this call. Probe: the instance directory kept its files after `remove(v=True)`, and `containers.get(name)` then raised `docker.errors.NotFound` with `status_code == 404`. Disposing of the instance's data is a separate, explicit act: `client.volumes.get(name).remove()` for the named volumes and a filesystem delete for the directory.

**status.** `container.reload()` then `container.status` or `container.attrs["State"]`. `Status` "Can be one of `created`, `running`, `paused`, `restarting`, `removing`, `exited`, or `dead`", and the spec warns to "Use the `Status` field instead" of `Running` because a paused container is both running and paused (v1.56 spec, ContainerState). `State.Health.Status` adds `starting`, `healthy`, `unhealthy` when a healthcheck is set. To find the hub's containers without a stored id: `client.containers.list(all=True, filters={"label": "kinby.hub=<id>"})`; "By default, only running containers are shown" (v1.56 spec, ContainerList). Probe: the label filter found the running container, found nothing after stop without `all=True`, and found it again with `all=True`.

**logs.** `container.logs(stdout=True, stderr=True, stream=False, tail="all", since=None, follow=False, timestamps=False)`; "Returns: (generator or str)". Probe: `tail=2` returned the last two lines; `stream=True, follow=True` yielded frames one at a time until the container exited. The logs live on the daemon for the life of the container, across stop and start, which the Kubernetes side does not match (below).

**exec** (not in the ticket, needed). `container.exec_run(cmd, stream=False, demux=False, ...)` runs a process in the container and returns its exit code and output (https://docker-py.readthedocs.io/en/stable/containers.html#docker.models.containers.Container.exec_run). `codex login --device-auth` is an interactive flow that prints a URL and a code and waits; `exec_run` with `stream=True` shows the output, and the user completes the login in the browser. The "is a coding client running" check is `container.top()` and a grep of the process list, which is exactly what `docker/update.sh` does.

## Verb by verb on Kubernetes

The objects, per instance, are one Secret, one PersistentVolumeClaim, one Deployment, one Service and optionally one Ingress, all in the hub's namespace and all carrying the same labels. The recommended label set is `app.kubernetes.io/name`, `app.kubernetes.io/instance` ("A unique name identifying the instance of an application"), `app.kubernetes.io/managed-by` ("The tool being used to manage the operation of an application") (https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/); `name=kinby`, `instance=<id>`, `managed-by=kinby-hub`. A `kinby.instance` label on top keeps the Docker and Kubernetes selectors identical.

**create.**

- Secret. Type `Opaque` is for "arbitrary user-defined data"; `stringData` takes plain text and Kubernetes base64-encodes it into `data`. The pod consumes it with `envFrom: [{secretRef: {name: ...}}]`, which exposes every key as an environment variable. Env values "are NOT updated when the Secret changes. They are set at Pod creation time", unlike mounted files (https://kubernetes.io/docs/concepts/configuration/secret/). That matches the Docker side, where env is fixed at create, so a secret rotation is a stop and start on both.
- PersistentVolumeClaim. `ReadWriteOnce`: "the volume can be mounted as read-write by a single node. ReadWriteOnce access mode still allows multiple pods to access the volume when the pods are running on the same node"; `ReadWriteOncePod`: "read-write by a single Pod ... only supported for CSI volumes and Kubernetes version 1.22+" (https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes). One claim at `/instance` holds the manifest, memory, `.state/` and the workspace. Compose's separate workspace volume existed for bind-mount performance, which a PVC does not suffer; `/root/.codex` can be a `subPath` of the same claim or a second small claim.
- Deployment. `replicas: 0` at create (the "created, not running" state), `strategy: {type: Recreate}`, a selector on the labels above, and a pod template with the image, `command: ["serve"]` (the image's entrypoint is `kinby-entrypoint`), `envFrom` the Secret, `volumeMounts` of the claim at `/instance`, and a `readinessProbe` and `livenessProbe` of `httpGet: {path: /health, port: 8787}` ("The diagnostic is considered successful if the response has a status code greater than or equal to 200 and less than 400", https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/). `Recreate` is not optional: "If `.spec.strategy.type==Recreate`, all existing Pods are killed before new ones are created when `.spec.template` is changed" (https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#strategy), and the single-instance stateful task page says why: "Rolling updates will not work, as you cannot have more than one Pod running at a time. The `Recreate` strategy will stop the first pod before creating a new one" and "Don't scale the app. This setup is for single-instance apps only. The underlying PersistentVolume can only be mounted to one Pod" (https://kubernetes.io/docs/tasks/run-application/run-single-instance-stateful-application/). A StatefulSet is for "Stable, unique network identifiers", "Ordered, graceful deployment and scaling" and `volumeClaimTemplates` (https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/); one instance needs none of that, and a Deployment with an explicit claim lets the hub own the claim's lifecycle.
- Service. `type: ClusterIP` is the default; the selector matches the pod labels; `port: 8787`, `targetPort: 8787`; the name resolves as `<service>.<namespace>.svc.cluster.local` and as `<service>` inside the namespace (https://kubernetes.io/docs/concepts/services-networking/service/). This is the Caddy network's counterpart: the ingress controller reaches `kinby-<id>:8787` by Service name.
- Ingress. One rule with a host or a path prefix and `backend: {service: {name: kinby-<id>, port: {number: 8787}}}`, `ingressClassName` naming the controller; "Only creating an Ingress resource has no effect" without a controller, and the API "has been frozen" with Gateway API as the successor (https://kubernetes.io/docs/concepts/services-networking/ingress/). Ingress is enough for one HTTPS name per instance; the Runtime should treat exposure as a spec field (`public_host`, optional) so the Docker side can feed a Caddy route and the Kubernetes side an Ingress rule or, later, an HTTPRoute.
- Ownership. "Kubernetes sets the value of this field automatically for objects that are dependents of other objects like ReplicaSets, DaemonSets, Deployments" and "You can also configure these relationships manually by changing the value of this field"; "A namespaced owner **must** exist in the same namespace as the dependent" (https://kubernetes.io/docs/concepts/overview/working-with-objects/owners-dependents/). Setting `ownerReferences` on the Secret, Service and Ingress pointing at the Deployment makes `remove` one delete. The claim is deliberately left without an owner so that removing the runtime never removes the data by accident.

Seeding the instance directory. On Docker the hub writes `kinby.toml` into the directory before create. On Kubernetes the hub cannot write into a claim it does not mount. The entrypoint already "prepares the mounted instance" (ADR 0003), so the clean extension is a seed: the spec carries the files, the Docker implementation writes them to the directory, the Kubernetes implementation ships them as a ConfigMap mounted read-only at `/seed`, and the entrypoint copies `/seed` into `/instance` when `/instance/kinby.toml` is absent. Same rule as the workspace clone: first boot only, never overwrite.

**start and stop.** `AppsV1Api.patch_namespaced_deployment_scale(name, namespace, body)` with `{"spec": {"replicas": 1}}` or `0` (https://github.com/kubernetes-client/python/blob/master/doc/html/kubernetes.aio.client.api.apps_v1_api.html). Scaling to zero keeps the Deployment, the claim, the Secret and the Service; only the Pod goes. Termination sends SIGTERM and waits `terminationGracePeriodSeconds` (default 30) before SIGKILL (https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/); that field is the Docker `stop(timeout=)` counterpart and belongs in the pod template.

**remove.** `AppsV1Api.delete_namespaced_deployment(name, namespace, propagation_policy="Foreground")` removes the ReplicaSet and Pod through their owner references and, with the manual owner references above, the Secret, Service and Ingress. `CoreV1Api.delete_namespaced_persistent_volume_claim` only when the caller asks for the data to go.

**status.** `CoreV1Api.list_namespaced_pod(namespace, label_selector="kinby.instance=<id>")`, then `pod.status.phase` (`Pending`: "one or more containers has not been set up and made ready to run"; `Running`: "At least one container is still running, or is in the process of starting or restarting"; `Failed`; `Unknown`) and the container state (`Waiting` with a reason such as an image pull error, `Running`, `Terminated`) plus the readiness condition (https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/). No pod and `replicas: 0` on the Deployment is "stopped"; no Deployment is "absent". This is where the two runtimes differ most and why the Protocol returns its own small status type instead of either vocabulary.

**logs.** `CoreV1Api.read_namespaced_pod_log(name, namespace, follow=True, tail_lines=N, since_seconds=S, timestamps=True, _preload_content=False)`; `_preload_content=False` returns "the urllib3.HTTPResponse object ... without reading/decoding response data" so the caller can iterate it (https://github.com/kubernetes-client/python/blob/master/kubernetes/docs/CoreV1Api.md). Two differences from Docker: the log belongs to the Pod, so after a stop and start the previous Pod's output is gone (`previous=True` only reaches the last terminated container of the same Pod), and stdout and stderr come interleaved unless `stream="Stdout"` or `"Stderr"` is passed. A hub that wants history across restarts on Kubernetes needs the cluster's log stack; the Protocol should promise "the current run's log", which both runtimes can keep.

**exec.** `kubernetes.stream.stream(CoreV1Api.connect_get_namespaced_pod_exec, name, namespace, command=[...], stdin=..., stdout=True, stderr=True, tty=False)` over the API server's WebSocket (https://github.com/kubernetes-client/python/blob/master/examples/pod_exec.py). The Codex device-code login works the same way as on Docker: run it, show the URL and code, wait.

**Client.** `kubernetes` 36.0.3 (2026-07-13, Apache-2.0, `Requires-Python >=3.10`, classifiers through 3.14; depends on `requests`, `urllib3`, `websocket-client`, `pyyaml`, `aiohttp` and others; https://pypi.org/project/kubernetes/). "client 36.y.z: Kubernetes 1.35 or below (+-), Kubernetes 1.36 (✓), Kubernetes 1.37 or above (+-)" (https://github.com/kubernetes-client/python). Config comes from `load_kube_config()` on a workstation or `load_incluster_config()` inside the cluster, where the hub's ServiceAccount needs a namespaced Role with `create`, `get`, `list`, `watch`, `patch`, `delete` on `deployments`, `deployments/scale`, `persistentvolumeclaims`, `secrets`, `services`, `configmaps`, `ingresses`, `pods`, `pods/log` and `pods/exec`, bound with a RoleBinding: "if you want to define a role within a namespace, use a Role" (https://kubernetes.io/docs/reference/access-authn-authz/rbac/). The README's asyncio example imports `from kubernetes.aio import client, config` and uses `async with ApiClient() as api` (https://github.com/kubernetes-client/python/blob/master/README.md); probe: `kubernetes.aio.client.AppsV1Api` imported on 3.14. So the Kubernetes implementation can be async-native while the Docker one uses threads, and the Protocol is async either way.

## The Runtime Protocol

What both runtimes need in and give out, and nothing else:

```python
from collections.abc import AsyncIterator, Mapping, Sequence
from dataclasses import dataclass, field
from typing import Literal, Protocol


@dataclass(frozen=True)
class InstanceSpec:
    instance_id: str                       # label value and object name stem
    image: str
    command: Sequence[str] = ("serve",)
    env: Mapping[str, str] = field(default_factory=dict)   # parsed from the instance .env by the hub
    port: int = 8787
    files: Mapping[str, str] = field(default_factory=dict)  # relative path -> content, seeded on first boot
    public_host: str | None = None         # a Caddy route or an Ingress rule when set
    stop_grace_seconds: int = 30


@dataclass(frozen=True)
class RuntimeStatus:
    state: Literal["absent", "created", "starting", "running", "stopped", "failed"]
    healthy: bool | None                   # None when the runtime reports no health
    detail: str = ""                       # the runtime's own words: "exited (137)", "ImagePullBackOff"


class Runtime(Protocol):
    async def create(self, spec: InstanceSpec) -> None: ...
    async def start(self, instance_id: str) -> None: ...
    async def stop(self, instance_id: str) -> None: ...
    async def remove(self, instance_id: str, *, delete_data: bool = False) -> None: ...
    async def status(self, instance_id: str) -> RuntimeStatus: ...
    def logs(self, instance_id: str, *, tail: int | None = None, follow: bool = False) -> AsyncIterator[bytes]: ...
    async def exec(self, instance_id: str, command: Sequence[str]) -> AsyncIterator[bytes]: ...
    async def list(self) -> Sequence[str]: ...   # instance ids the runtime holds under the hub's label
```

Why this shape:

- The instance id is the only handle. Docker resolves it to a container by name (`kinby-<id>`) or by the `kinby.instance` label; Kubernetes resolves it to object names and a label selector. No container id, pod name or host path crosses the seam, so the hub's registry stores the spec and what the hub decided, not what the runtime assigned. `list()` lets the hub reconcile its registry against the runtime's labels after a restart, which is what the label is for.
- `env` is a mapping, not a file path. Reading the `.env` is the hub's job (`dotenv_values`); Docker passes it as `environment`, Kubernetes writes a Secret. A path would leak the Docker bind-mount assumption.
- `files` seeds the instance directory. The Docker implementation writes them into the bind directory, the Kubernetes implementation ships a ConfigMap for the entrypoint to copy. Neither mounts anything the hub named.
- `delete_data` is explicit on `remove`. Both runtimes keep data by default (a bind directory and named volumes; a claim without an owner), and both can delete it when told.
- `status` returns the small vocabulary. The mapping is: Docker `created` to `created`, `running` with health `starting` to `starting`, `running` to `running`, `exited` after a hub stop to `stopped`, `exited` or `dead` otherwise to `failed`, `restarting` to `starting`, no container to `absent`. Kubernetes: no Deployment to `absent`, `replicas: 0` with no pod to `stopped` or `created` (the hub knows which it asked for), `Pending` or `Waiting` to `starting`, `Running` and ready to `running`, `Running` and not ready to `starting` with `healthy=False`, `Failed` or a waiting reason like `CrashLoopBackOff` to `failed`. `detail` carries the runtime's own text so nothing is lost.
- `logs` and `exec` are async iterators of bytes. Docker's frames and Kubernetes' chunks both fit; line splitting and decoding are the hub's, not the runtime's.
- What stays out: image builds (the box builds with Compose today, ADR 0030 rejects a registry for the first deploy; the hub can call `images.build` later behind a different seam), network and ingress creation beyond the spec's `public_host`, and anything about restart policies or probes, which each implementation sets from its own defaults.

The Caddy side is the one thing this leaves open on Docker. The Caddyfile hardcodes `reverse_proxy coder:8787`; per-instance routes need either a directory of snippets the Caddyfile `import`s plus a reload (https://caddyserver.com/docs/caddyfile/directives/import), or the Caddy admin API (https://caddyserver.com/docs/api). That is a hub build detail, not a Runtime one; the Runtime's part is done once the container is on the network under a predictable name.

## The hub's state: SQLite or Postgres

The hub keeps the instance registry (specs, what it asked each runtime to do), and the web token. That is a few tables with one writer, the hub process. SQLite's own guidance: "SQLite supports an unlimited number of simultaneous readers, but it will only allow one writer at any instant in time" and "any site that gets fewer than 100K hits/day should work fine with SQLite" (https://www.sqlite.org/whentouse.html). The cases it names for a client/server engine are "many client programs sending SQL to the same database over a network" and "Many concurrent writers". A single-user hub has neither, and multi-user hubs are out of scope on the map.

On Docker nothing changes: the database sits in the hub directory, a bind mount or a named volume, exactly like each instance's `.state/checkpoints.sqlite` (ADR 0015).

On Kubernetes the question is only whether the volume behaves like a local disk. SQLite's locking page: "POSIX advisory locking is known to be buggy or even unimplemented on many NFS implementations" and "Your best defense is to not use SQLite for files on a network filesystem" (https://www.sqlite.org/lockingv3.html); and for WAL, "All processes using a database must be on the same host computer; WAL does not work over a network filesystem" (https://www.sqlite.org/wal.html). A ReadWriteOnce claim on a block-backed class (cloud disks through CSI, `local`, `hostPath`, iSCSI, Fibre Channel all list RWO; https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes) is a filesystem formatted on a disk attached to one node: locks and fsync are the kernel's, not a network server's. NFS is the type that lists ReadWriteMany, and that is the case SQLite rules out. So the hub runs as one Deployment with `replicas: 1`, `strategy: Recreate` and a ReadWriteOnce claim, the same shape as an instance and as the single-instance MySQL task page. Two rules follow: the hub's storage class must be block-backed, never an NFS-backed RWX class, and `Recreate` is mandatory so a rollout never has two hub pods on one database.

The instances make the same demand already. Every instance carries `checkpoints.sqlite` on its own claim, so a cluster that cannot give the hub a block-backed RWO claim cannot run an instance either. Moving the hub to Postgres would not lift that constraint; it would add a Postgres Deployment, a claim, a Secret, backups and migrations to keep a few tables that one process writes.

A concrete Kubernetes reason for Postgres would be one of: more than one hub replica (multi-user, out of scope), or a hosting target whose only storage is NFS or object storage (then the instances are the first problem). Neither is on the map. SQLite stays.

## Recommendation

- Docker: `docker` 7.2.0 through `docker.from_env()`, wrapped in `asyncio.to_thread`. Create with `labels={"kinby.hub": ..., "kinby.instance": ...}`, `environment=dotenv_values(instance/.env)`, `mounts=[Mount("/instance", <host path>, type="bind"), Mount("/instance/workspace", "kinby-<id>-workspace", type="volume"), Mount("/root/.codex", "kinby-<id>-codex", type="volume")]`, `network=<compose network, "kinby_default" on the box>`, `restart_policy={"Name": "unless-stopped"}`, the `/health` healthcheck, and no published port. Find containers by label with `all=True`; never touch `compose.yaml` or Compose labels; the cron `--remove-orphans` ignores hub containers because they carry no Compose project label. Write into the hub spec that the socket is root on the box.
- Kubernetes: per instance one Opaque Secret (`envFrom`), one RWO claim at `/instance`, one Deployment (`replicas` 0 at create, `Recreate`, readiness and liveness on `/health`, `terminationGracePeriodSeconds` from the spec), one ClusterIP Service on 8787, one Ingress rule when `public_host` is set, owner references from Secret, Service and Ingress to the Deployment, none on the claim. `kubernetes` 36.0.3 with `kubernetes.aio`, `load_incluster_config`, a namespaced Role. Seed the instance directory through a ConfigMap at `/seed` that the entrypoint copies on first boot.
- Protocol: the `InstanceSpec`, `RuntimeStatus` and `Runtime` above, async throughout, with `exec` and `list` added to the six verbs in the ticket and `delete_data` explicit on `remove`. Instance id in, runtime vocabulary never out.
- State: SQLite in the hub directory, on a named volume or bind mount on Docker and on a block-backed ReadWriteOnce claim on Kubernetes, with the hub as a single-replica `Recreate` Deployment. Refuse NFS-backed classes for the hub and for instances alike. No Postgres.
- Open for the hub's build tickets, not for this research: the Caddy route per instance (snippet import or admin API), where the Docker implementation gets the host path of the instances directory when the hub itself is a container, and the entrypoint's seed step.
