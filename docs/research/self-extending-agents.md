# Self-extending personal agents: Hermes Agent and OpenClaw

Wayfinder ticket: jorgesolerrr/kinby #518 (map #516). Date: 2026-10-03.

Question: how do Hermes Agent (Nous Research) and OpenClaw let their main agent extend itself and its system (skills, tools, sub-agents, schedules, channels)? For each: what it can create, how creation is approved or sandboxed, how created things are stored and versioned, what asking for one looks like, how it acts on the user's behalf, and whether MCP is load-bearing. Then: what kinby's home instance could borrow.

Sources are the projects' own repositories, read at fixed commits:

- Hermes Agent: [`NousResearch/hermes-agent@343500b`](https://github.com/NousResearch/hermes-agent/tree/343500b3547e12530457c2fda60ec687e25118b4) (docs under `website/docs/`). Links below abbreviate this as `H:`.
- OpenClaw: [`openclaw/openclaw@6b230c8`](https://github.com/openclaw/openclaw/tree/6b230c82fc52161e644b9e94c17dd30ccc680b72) (docs under `docs/`). Links below abbreviate this as `O:`.

`H:path` means `https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/path`. `O:path` means `https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/path`. Both are the projects' own docs. Neither was checked against running code, so a claim that rests on a doc is as good as that doc.

## Short answer

1. **Skills are the one thing both let the agent create freely.** Each has a dedicated write tool (`skill_manage` in Hermes, `skill_workshop` in OpenClaw), a background "learn from this session" pass, and an optional review queue. Hermes writes immediately by default and can stage writes for approval. OpenClaw stages a hash-bound proposal and only `apply` makes it live.
2. **Schedules are second.** Both expose one scheduler tool (`cronjob_manage`, `automations`/`cron`) that the main agent uses from plain-language requests. Both stop scheduled or sub-agent runs from creating more schedules by default.
3. **Neither lets the agent author native tools through a governed path.** Tools come from plugins that a human enables (Hermes `plugins.enabled`, OpenClaw trusted install sources). The agent gets new capability by writing scripts it runs through existing tools: Hermes `execute_code` and no-agent cron scripts, OpenClaw Lobster pipelines.
4. **Sub-agents are ephemeral, and persistent agents are the operator's.** Both spawn isolated children with a hard-denied tool set (no scheduling, messaging or memory writes) and a depth cap. Persistent agents (Hermes profiles/Bots, OpenClaw agents) are created by the operator. **OpenClaw is the exception that matters for kinby.** A regular agent can ask a privileged *system agent* to create another agent through one typed tool. The system agent executes the request, the human approves under the requesting run's permission mode, and the new agent records the requester as its creator.
5. **MCP is not load-bearing for self-extension in either.** Both are MCP clients for third-party tools, configured in config files. OpenClaw also uses MCP to hand its single privileged tool to CLI harnesses such as Claude Code. The creation paths themselves are native tools.

### How creation is approved or sandboxed

- **Skills write freely by default.** `skills.write_approval: true` stages every `skill_manage` write under `~/.hermes/pending/skills/`, reviewed with `/skills pending`, `/skills diff`, `/skills approve|reject` ([H:user-guide/features/skills.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/skills.md), "Gating agent skill writes"). A separate `skills.guard_agent_created` is a content scanner, not an approval gate (same section). An advisory linter runs on every write and never blocks it (same page, "What a skill entry looks like").
- **Schedules have no approval step.** The limits are structural instead. Cron runs cannot use `cronjob_manage` unless `cron.allow_agent_scheduling: true` ("to prevent runaway scheduling loops"). The agent can pin a job to the current model only when the user asks, and cannot point a job at a different model ("inference pins are user-owned"). Reasoning effort is not exposed on the tool. Prompts are scanned for injection and exfiltration patterns at create and update time. ([H:user-guide/features/cron.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/cron.md))
- **Dangerous shell commands** go through `approvals.mode` (`smart` uses an auxiliary LLM to auto-approve low risk, auto-deny high risk and escalate the rest; `manual`; `off`). Headless contexts use `cron_mode`, `single_query_mode` and `unattended_mode`, all `deny` by default. A hardline blocklist applies regardless. ([H:user-guide/security.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/security.md), "Dangerous Command Approval")
- **File writes** hit a protected-path denylist (credential stores, Hermes secret files) with no approval prompt. The docs call this "defense-in-depth, not a hard boundary", because `terminal` runs as the same OS user. The docs tell the agent to change cron state through `cronjob_manage`, not by patching `jobs.json`. ([H:user-guide/security.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/security.md), "File Write Safety")
- **Catalog installs** (`manage_catalog`, `manage_connections`) show one approval card per item. "The model cannot pass a source, commit, profile or setting." Installs come from the catalog's reviewed commit after a security scan. `manage_catalog` belongs to a `setup` toolset. The backend grants it only to a profile whose `profile.yaml` carries `role: setup` and strips it from every other profile, "even when a config list … or `all` names it". ([H:reference/tools-reference.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/reference/tools-reference.md), [H:reference/toolsets-reference.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/reference/toolsets-reference.md))
- **Sub-agents** inherit the parent's toolsets ("the model cannot grant a child capabilities that the parent does not have"). Leaf children cannot call `delegate_task`, `clarify`, `memory`, `send_message` or `cronjob`. Nesting is off by default (`max_spawn_depth: 1`). ([H:user-guide/features/delegation.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/delegation.md))

### Storage and versioning

- Skills live in `~/.hermes/skills/`, the "single source of truth". Agent-created and hub-installed skills land there too ([H:user-guide/features/skills.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/skills.md)). Bundled skills are tracked by an origin-hash manifest, so locally edited copies are not overwritten on update (same page, "Bundled skill updates"). Agent skill writes have no history beyond the staging queue. Neither doc mentions a git integration (**unverified** that none exists).
- The **curator** maintains agent-created skills in the background. It tracks use, marks unused skills `stale` after 14 days, and archives them after 30 into `~/.hermes/skills/.archive/` ("never auto-deletes"). It skips pinned skills and skills referenced by any cron job. An LLM consolidation pass is opt-in. ([H:user-guide/features/curator.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/curator.md))
- Cron jobs live in one flat, user-owned `~/.hermes/cron/jobs.json`. Jobs created by a scheduled run have "no special ownership". No-agent scripts must resolve inside `$HERMES_HOME/scripts/`. ([H:user-guide/features/cron.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/cron.md))

### What asking looks like

Plain language for schedules: "Every morning at 9am, check Hacker News for AI news and send me a summary on Telegram", and the agent calls `cronjob_manage`. For a watchdog ("Ping me on Telegram if RAM is over 85%, every 5 minutes") the agent writes the script with `write_file` and then creates a `no_agent` job ([H:user-guide/features/cron.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/cron.md)). Skills are created unprompted: the system prompt tells the agent to save a non-trivial workflow, a found fix, or a user correction ([H:user-guide/features/skills.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/skills.md)). `/learn` is the explicit form.

### Acting on the user's behalf

Delivery goes to the origin chat or a named platform target. A job created inside a cron run resolves `deliver: origin` at create time so it never points at a dead session ([H:user-guide/features/cron.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/cron.md)). Messaging goes through `send_message`, which sub-agents cannot call ([H:user-guide/features/delegation.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/delegation.md)).

### MCP

MCP is a client for external tool servers defined under `mcp_servers` in `config.yaml`, with a curated catalog and `manage_connections` for install and OAuth ([H:user-guide/features/mcp.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/user-guide/features/mcp.md), [H:reference/tools-reference.md](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/website/docs/reference/tools-reference.md)). Hermes can also serve MCP ([`mcp_serve.py`](https://github.com/NousResearch/hermes-agent/blob/343500b3547e12530457c2fda60ec687e25118b4/mcp_serve.py) at the repo root). None of the creation paths above runs through MCP.

### The system agent

OpenClaw ships a built-in **system agent** that "speaks as 'OpenClaw'" and handles setup, repair and configuration ([O:cli/openclaw.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/cli/openclaw.md)). It is restricted to "one ring-zero OpenClaw authority tool, `openclaw`, that wraps the typed operations". Read actions run freely. Mutations need approval for "that exact operation", and "every applied write is audited and re-validated" (same page, "AI conversation"). "The host does not parse natural-language requests into operations": the model maps a request onto a typed operation.

Which agent owns ambient system work is set by `agents.defaults.systemAgent.agentId` ([O:gateway/config-agents/heartbeat-compaction-and-streaming.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/gateway/config-agents/heartbeat-compaction-and-streaming.md)). Only that agent sees the release-shipped **Custodian skills** (`configure-channel`, `add-model-provider`, `diagnose-gateway`, …). Each follows a fixed Gather → Mutate → Repair → Prove → Report contract, and mutations go through "validated non-interactive writes, never a direct file edit". A `create-agent` playbook is on the roadmap, not shipped. ([O:tools/custodian-skills.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/custodian-skills.md))

A **regular agent** reaches the system agent through its own `openclaw` tool. That adds a separate model turn "through the running Gateway rather than launching the CLI" ([O:cli/openclaw.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/cli/openclaw.md)). For agent creation: "The system agent files the typed operation, shows the requesting agent id to the operator, and creates the agent only after operator approval" ([O:concepts/multi-agent.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/concepts/multi-agent.md), "Agent provenance").

### How creation is approved or sandboxed

- **Delegated persistent changes follow the requesting run's permission mode.** "Full Access applies the exact proposed operation automatically." Restricted runs from messaging channels ask in the requesting chat with native **Allow once / Deny** cards or `/approve <id> allow-once|deny`. "Replying 'yes' in the delegated chat cannot authorize a change; the button or `/approve` command does." The requesting tool stays open until a decision. Stopping the run cancels the approval, and a late approval cannot revive it. ([O:gateway/permission-modes.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/gateway/permission-modes.md), "Delegated setup and repair"; [O:cli/openclaw.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/cli/openclaw.md), "Operations and approval")
- **The system agent cannot approve itself.** In direct chat with it, approval phrases resolve from "a closed deterministic list". Ambiguous replies go to a separate completion call that sees only the reply and the proposal, "never by the conversation model itself, which cannot self-approve" ([O:cli/openclaw.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/cli/openclaw.md)).
- **Secrets never pass through the model by design.** An exact `config set` on a sensitive path "never reaches a model". Channel, search and gateway setup hand off to a masked terminal wizard when they reach a secret. A pasted key is moved to the secret store and referenced by a SecretRef. ([O:cli/openclaw.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/cli/openclaw.md))
- **Session permission modes**: `read-only`, `guarded` (human reviews exec escalations), `workspace` (an LLM reviewer can allow, deny, or ask a human; three consecutive denials escalate), `full` ([O:gateway/permission-modes.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/gateway/permission-modes.md)).
- **Skills**: Workshop proposals are stored as `PROPOSAL.md`. "Apply is the only live write." Update proposals bind to the target's hash and go `stale` if it changes. Apply reruns a security scanner that blocks only on critical findings, and rollback metadata is written first. ([O:tools/skill-workshop/how-it-works.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/skill-workshop/how-it-works.md)) Self-learning defaults to `auto`, where the background reviewer edits Workshop files directly with ordinary file tools rooted at the Workshop directory, without proposals or rollback snapshots. `propose` stages instead. ([O:tools/self-learning.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/self-learning.md), [O:tools/skill-workshop.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/skill-workshop.md))
- **Schedules**: conversational management requires an owner (`commands.ownerAllowFrom`) or a Control UI admin. Each operation uses "a one-use grant that expires after 60 seconds" bound to the active run ([O:automation/cron-jobs/managing-jobs.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/automation/cron-jobs/managing-jobs.md)).
- **Sub-agents** "always lose `gateway`, `agents_list`, `session_status`, `progress_card`, `cron`, `message`, `sessions_send`, and the `conversations_*` tools", and allow-lists cannot override that ([O:tools/subagents/tool-policy.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/subagents/tool-policy.md)).

### Storage and versioning

- Agents: each one has a workspace, an `agentDir` and a SQLite session store, all declared in `openclaw.json` ([O:concepts/multi-agent.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/concepts/multi-agent.md)). Provenance is recorded as `operator`, `agent` (with the requesting agent id) or `claw`. `openclaw agents list --tree` shows the creation hierarchy (same page).
- Config writes: applied system-agent operations and config writes, including manual edits to `openclaw.json`, are journaled in SQLite (`system-agent-audit`, `config-audit`; latest 50,000 each). The journal stores changed paths, not values ([O:cli/openclaw.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/cli/openclaw.md), "Change history").
- Skills: Workshop skills live in `<state-dir>/agents/<agentId>/agent/workshop-skills`, apart from the workspace. Proposal generations are immutable and published by atomic rename. Applied versions are retained for comparison, "not a complete edit timeline". ([O:tools/skill-workshop.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/skill-workshop.md), [O:tools/skill-workshop/how-it-works.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/skill-workshop/how-it-works.md))

### What asking looks like

- Schedules are usually **promoted**. When the user asks for the same job several times, the agent checks `automations(action: "list")` and offers a schedule. The confirmation is a plain sentence ("Every weekday at 07:00 Europe/Vienna, I summarize overnight updates and post them here"), not a cron expression. On confirmation the agent creates the job **enabled**, runs it once at once as a visible test, and removes it if the test fails. Creating it enabled is deliberate: "Nothing supervises a disabled job." ([O:automation/cron-jobs/how-it-works.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/automation/cron-jobs/how-it-works.md))
- Agents: from the Control UI, **New agent** opens "the custodian chat", where creation "waits for your approval" ([O:concepts/multi-agent.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/concepts/multi-agent.md)). From the TUI: `create agent work workspace ~/path/to/work` ([O:cli/openclaw.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/cli/openclaw.md)).
- Failure repair: when a job created from a conversation crosses its failure threshold, OpenClaw sends a repair request to that owner conversation instead of a bare alert. The request carries no sender identity, so it cannot change the job by itself ([O:automation/cron-jobs/delivery.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/automation/cron-jobs/delivery.md)).

### Acting on the user's behalf

**Standing orders** in `AGENTS.md` grant "permanent operating authority" for named programs, each with a scope, triggers, approval gates and escalation rules, combined with automations for timing ([O:automation/standing-orders.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/automation/standing-orders.md)). The team preset's role instructions "require human approval before external sends, publication, purchases, deletion, or production changes" ([O:concepts/multi-agent.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/concepts/multi-agent.md)).

### MCP

MCP is a client for third-party servers under `mcp.servers`, subject to the same tool policy ([O:tools/mcp.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/mcp.md)). The one place MCP carries weight is CLI harnesses: Claude Code runs the system agent "with an empty native-tool selection and one MCP tool, `openclaw`" under `--strict-mcp-config` ([O:cli/openclaw.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/cli/openclaw.md), "CLI harness trust model"). Sub-agent tools likewise reach a Claude CLI backend "only through OpenClaw's policy-filtered MCP surface" ([O:tools/subagents/tool-policy.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/subagents/tool-policy.md)). MCP is how OpenClaw hands its own tools to an external agent binary. It is not how the agent creates anything.

## Side by side

| | Hermes Agent | OpenClaw |
| --- | --- | --- |
| Skill writes | free by default; opt-in staging | hash-bound proposals; self-learning `auto` edits directly |
| Skill upkeep | curator: stale → archive, never delete | weekly collection review, Workshop rollback |
| Schedules from chat | yes, no approval | yes, a confirmed plain sentence, then a test run |
| Schedules from scheduled runs | off by default | management needs a fresh owner turn |
| Native tool authoring | no (plugins are user-enabled) | no (plugins from trusted sources) |
| Agent creates agents | no model path | yes, through the system agent, approved, provenance kept |
| Privileged role | `role: setup` profile gets `manage_catalog` | `systemAgent` gets the `openclaw` tool and Custodian skills |
| Secrets and the model | env passthrough declared in config | masked wizards and SecretRefs, never in the prompt |
| MCP load-bearing | no | only as the transport to CLI harnesses |

## What kinby's home instance could borrow

Constraints from kinby: instance tools are gated core write tools over whole files ([ADR 0028](../adr/0028-instance-tools-are-gated-core-write-tools-over-whole-files.md)). The gate is per-tool rules under mode presets, and the thread's mode never exceeds the instance's ceiling ([ADR 0014](../adr/0014-gate-policy-is-per-tool-rules-under-mode-presets.md)). The hub owns instance lifecycles ([ADR 0033](../adr/0033-the-hub-owns-managed-instance-lifecycles.md)). "The access token never enters an instance, so an agent cannot call hub methods", and "the line that matters is that agents never hold hub scopes" ([ADR 0049](../adr/0049-a-cookie-session-for-the-browser-and-a-control-token-per-instance.md)).

1. **Keep the hub as the executor and give the home instance typed requests, not hub scopes.** This is OpenClaw's shape: the privileged tool files a typed operation, the host validates and applies it, and the requester is recorded. For kinby, the home instance's hub-level tools (`instance_create`, …) would send a typed request that the hub validates and applies, with the instance attached as creator. ADR 0049 still has to change: an instance can reach the hub today only as a target of the hub's control token, never as a caller. The home instance needs some caller credential or channel that is narrower than the access token. That decision belongs in a new ADR.
2. **Grant the role from outside the instance.** Hermes grants `manage_catalog` only to a profile marked `role: setup` and strips it everywhere else, "even when a config list … names it". OpenClaw picks its system agent in gateway config, not in the agent's own files. kinby's equivalent: the hub registry records which instance is the home instance, and the hub decides whether that instance gets the hub tools. A manifest the agent can edit through instance tools must not be able to promote an instance.
3. **Let the gate decide, with the requesting thread's mode.** OpenClaw applies a delegated change under the requesting run's mode: full access applies it, restricted runs ask with a button. This matches ADR 0014 and the 0028 decision against a stricter tier. Two details worth keeping: approval comes from the approval control, never from a chat "yes", and a request dies with its run, so a late approval cannot revive it.
4. **Approve the exact operation, and let the model choose fewer fields than the user can.** Hermes: "The model cannot pass a source, commit, profile or setting", and inference pins on cron jobs are "user-owned". For `instance_create`, the model could choose a package and a name. The package pin, secrets and model choice stay in the app's form, which fits ADR 0064 (clients send configuration values and the instance writes the files).
5. **Keep secrets out of the model's path.** OpenClaw hands off to a masked wizard at the first secret field. When the home instance creates an instance that needs a token, the operation should end in a pending setup the user finishes in the web app, not in a chat message.
6. **Promote repeats into routines, created enabled and tested once.** OpenClaw's promotion flow fits the existing `routine_write`. The agent confirms a plain sentence, writes the routine enabled, runs it once at once into the same thread, and deletes it if that run fails. ADR 0022's failure policy already supervises enabled routines. This also covers the "one-shot reminders" item on the map.
7. **Stop routine wakes from creating routines.** Both projects block this by default. ADR 0028 keeps instance tools on routine and signal wakes and leaves them to the routine's `mode`. The home instance's hub-level tools could be removed on non-interactive wakes, which closes the runaway-creation loop without a new mode.
8. **Record provenance and an audit trail.** OpenClaw's `agents list --tree` and its config journal correspond to a `created_by` on the hub's instance record plus the existing `tool.call` and gate-decision events ([ADR 0026](../adr/0026-model-calls-and-gate-decisions-are-events.md)). No new store is needed.
9. **Leave native tools to people.** Neither project lets the agent author a native tool, which supports ADR 0028's deferral. The home instance can extend capability through skills, routine code steps and packages. A skill that bundles a script covers most "make me a tool" requests.
10. **Do not add MCP for this.** Nothing in either creation path depends on it. MCP becomes relevant only if a delegated Claude Code run (the coder) should call kinby tools. OpenClaw's strict, single-tool MCP surface is the model for that case.

Also relevant to the map, though outside this question: OpenClaw's `show_widget` with `pin: true` pins an agent-rendered widget or a native report to a dashboard, served from a sandboxed origin ([O:tools/show-widget.md](https://github.com/openclaw/openclaw/blob/6b230c82fc52161e644b9e94c17dd30ccc680b72/docs/tools/show-widget.md)). It is a reference for the per-instance **views** item and its unnamed generative-UI concept.
