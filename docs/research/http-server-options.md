# asyncio HTTP server options for the signal receiver

Wayfinder ticket: jorgesolerrr/kinby #125. Date: 2026-09-06.
Question: which asyncio-native HTTP server library does kinby adopt for the signal receiver, given that the server effort will later put an RPC-over-WebSocket socket in front of the dispatcher in the same `kinby serve` process?

Sources: the docs and source of aiohttp 3.14.3, Starlette 1.6.0, uvicorn 0.52.4, Hypercorn 0.18.0 and Granian 2.8.2 (the versions `uv` resolves for Python 3.14 today), their PyPI metadata, and the ASGI spec. Three background agents read the docs and source on GitHub; every claim below names its file or page. On top of the reading, each candidate except Granian was installed into a scratch venv on CPython 3.14.2 and exercised with a probe script covering every requirement in the ticket: start on a running loop, ephemeral port, raw body, oversize body, WebSocket on the same port, stop timing. Probe results are marked "probe" below. Probes ran on Windows; the signal-handler findings come from the source, which is platform-independent.

## Short answer

Adopt aiohttp, used through `web.AppRunner` and `web.TCPSite` on the loop `kinby serve` already runs. It is the only candidate that meets every requirement in the ticket without application code or a private API. It neither creates a loop nor touches signal handlers. It reports the port it bound through a public property. `await runner.cleanup()` returns when the last connection is gone, with no polling tick. `client_max_size` already defaults to one megabyte and answers 413 from the same `request.read()` that yields the raw bytes for the HMAC check. A WebSocket handler is one more GET route on the same router. Ten releases in the last twelve months, Python 3.14 supported since October 2025, Apache-2.0.

The trade-off is footprint and portability. aiohttp brings eight packages, five of them with C extensions (with pure-Python fallbacks), against six for Starlette and uvicorn without WebSocket support. Its handler API is its own, not ASGI, so the later WebSocket socket is written against `web.WebSocketResponse` and cannot be moved to another server without a rewrite. For a single-process, single-user receiver that will host at most a few connections, that portability is not worth the two things the ASGI route costs at the seam: uvicorn replaces the process's SIGINT and SIGTERM handlers while it serves, and it notices a stop request on a 100 ms timer.

## The seam this has to fit

`kinby serve` is `_serve_instance` in `src/kinby/cli/main.py`: it registers SIGINT and SIGTERM with `loop.add_signal_handler(..., stopping.set)`, boots the runtime (scheduler and recap writer as tasks on the same loop), and awaits `stopping`. The receiver is one more thing started in that boot and stopped in its `finally`. Two consequences fix the evaluation:

- Anything that installs its own signal handlers competes with `stopping`. The library must leave signals alone.
- Stop has to be an awaitable that returns when the sockets are closed and in-flight handlers are done, so `finally` can await it and a test can await it after an ephemeral-port bind. A library that polls a flag on a timer adds a sleep the test cannot avoid.

## aiohttp 3.14.3

Runs on the existing loop. The docs separate the two entry points: "`run_app` provides a simple *blocking* API for running an `Application`. For starting the application *asynchronously* or serving on multiple HOST/PORT `AppRunner` exists", with the four-line recipe `runner = web.AppRunner(app); await runner.setup(); site = web.TCPSite(runner, host, port); await site.start()` and "To stop serving call `AppRunner.cleanup`" (https://docs.aiohttp.org/en/stable/web_advanced.html#application-runners). `run_app` does own a loop: `if loop is None: loop = asyncio.new_event_loop()`, then `run_until_complete` and `loop.close()` in its `finally` (`aiohttp/web.py`, `run_app`). `AppRunner._make_server` calls `asyncio.get_event_loop()` from inside the coroutine, so it picks up whichever loop is running (`aiohttp/web_runner.py`).

Signals. `BaseRunner.__init__(self, *, handle_signals: bool = False, shutdown_timeout: float = 60.0, **kwargs)`; only with `handle_signals=True` does `setup()` call `loop.add_signal_handler` for SIGINT and SIGTERM (`aiohttp/web_runner.py`, `BaseRunner.setup`). The docs say the same: "add signal handlers for `signal.SIGINT` and `signal.SIGTERM` (`False` by default)" (https://docs.aiohttp.org/en/stable/web_reference.html#aiohttp.web.AppRunner). Probe: the handlers for both signals were identical before and after `setup()` and `start()`.

Ephemeral port. `TCPSite.start()` passes the port to `loop.create_server` and then stores `self._server.sockets[0].getsockname()[1]`; the public property `TCPSite.port` returns it, documented as "the actual port number the server is bound to" (`aiohttp/web_runner.py`, `TCPSite.start` and `TCPSite.port`; https://docs.aiohttp.org/en/stable/web_reference.html#aiohttp.web.TCPSite). `BaseRunner.addresses` lists every bound address. `SockSite` accepts a pre-bound `socket.socket` when the caller wants to own the bind. Probe: `port=0` bound, `runner.addresses` reported `[('127.0.0.1', 49379)]`.

HTTP and WebSocket on one port. "To setup a *WebSocket*, create a `WebSocketResponse` in a request handler" and "The handler should be registered as HTTP GET processor" (https://docs.aiohttp.org/en/stable/web_quickstart.html#websockets). So `/signals/<routine>`, `/health` and a future `/ws` are three routes in one `UrlDispatcher` on one `TCPSite`. Probe: `POST /signals/x`, `GET /health` and a WebSocket echo on `/ws` all served from one `Application`.

Python 3.14. Changelog 3.13.0 (2025-10-06): "Added support for Python 3.14" and "Added support for free-threading in Python 3.14+" (https://docs.aiohttp.org/en/stable/changes.html). 3.14.3 carries the `Programming Language :: Python :: 3.14` classifier and `Requires-Python: >=3.10` (installed `METADATA`). Wheels for cp314 exist; the venv installed `_http_parser.cp314-win_amd64.pyd` and friends.

Footprint, license, maintenance. Runtime requirements on 3.13+: `aiohappyeyeballs`, `aiosignal`, `attrs`, `frozenlist`, `multidict`, `propcache`, `yarl` (installed `METADATA`; `async-timeout` and `typing_extensions` are gated to older Pythons). `yarl` pulls `idna`, so the resolved set is eight packages plus aiohttp itself. C extensions: aiohttp (`_http_parser`, `_http_writer`, two websocket helpers), multidict, yarl, frozenlist, propcache; each has a pure-Python build selected by an `*_NO_EXTENSIONS` variable, and `aiohttp/http_parser.py` falls back when the extension import fails. Licenses: aiohttp `Apache-2.0 AND MIT` (the MIT part is vendored llhttp), multidict, yarl, frozenlist, aiosignal, propcache Apache-2.0, attrs MIT, aiohappyeyeballs PSF-2.0. Releases in the last twelve months: 3.13.0 through 3.13.5 and 3.14.0 through 3.14.3, ten in all, the last on 2026-07-22 (https://github.com/aio-libs/aiohttp/releases). Maintained by the aio-libs org with five PyPI maintainers. `py.typed` shipped; the project's own mypy config is strict.

Raw body. `BaseRequest.read()`: "Read request body, returns bytes object with body content", and "The method does store read data internally, subsequent read() call will return the same value" (https://docs.aiohttp.org/en/stable/web_reference.html#aiohttp.web.BaseRequest.read). The source loops `await self._payload.readany()` into a `bytearray` and returns `bytes` (`aiohttp/web_request.py`, `read`). `text()` and `json()` are separate opt-in calls. What the parser does before the handler is transport work: it de-chunks, and with the default `auto_decompress=True` it inflates `gzip`, `deflate`, `br` and `zstd` content encodings (`aiohttp/http_parser.py`, `HttpParser.parse_headers`; `aiohttp/web_protocol.py`, `RequestHandler.__init__`). No webhook sender compresses a signed body, and `Application(handler_args={"auto_decompress": False})` turns it off if one ever does. Probe: a body of `b"\x00\xffraw"` came back byte-for-byte.

Body cap. `Application(client_max_size: int = 1024**2)` with the docs: "client's maximum size in a request, in bytes. If a POST request exceeds this value, it raises an `HTTPRequestEntityTooLarge` exception" (https://docs.aiohttp.org/en/stable/web_reference.html#aiohttp.web.Application). In `read()`, after every chunk: `if body_size > self._client_max_size: raise HTTPRequestEntityTooLarge(self._client_max_size)`, and `HTTPRequestEntityTooLarge.status_code = 413` with the text "Maximum request body size {max_size} exceeded." (`aiohttp/web_request.py`, `read`; `aiohttp/web_exceptions.py`). Two limits of that design: the cap is enforced when the handler reads, not at the protocol, so it measures the decompressed size and does not apply to a handler streaming `request.content` itself; and `client_max_size=0` disables it. Both are fine for a handler that always calls `read()`. Probe: with `client_max_size=1024`, a 2 KiB body with `Content-Length` and a 2 KiB chunked body both got 413 with that text; a 3-byte body got 200.

Start and stop. The "Graceful shutdown" section lists the steps and says "if using a runner, then calling `AppRunner.cleanup` will perform these steps": stop the sites so new connections are rejected, close idle keep-alive connections and mark active ones to close on completion, fire `on_shutdown` (the place to close WebSockets), wait `shutdown_timeout` for running handlers, cancel what remains, fire `on_cleanup` (https://docs.aiohttp.org/en/stable/web_advanced.html#graceful-shutdown). The source is one chain of awaits: `site.stop()` per site, `await asyncio.sleep(0)`, `server.pre_shutdown()`, `app.shutdown()`, `server.shutdown(self._shutdown_timeout)`, `app.cleanup()` (`aiohttp/web_runner.py`, `BaseRunner.cleanup`). `Server.shutdown` gathers `conn.shutdown(timeout)` over open connections (`aiohttp/web_server.py`). There is no timer loop; `cleanup()` returns as soon as the connections are gone, bounded by `shutdown_timeout` (set on the runner; setting it on a site is deprecated). Probe: `cleanup()` with an idle keep-alive connection still open returned in under a millisecond. `AppRunner(app, handler_cancellation=True)` cancels a handler when its client disconnects; leave it at the default so a signal turn is not cancelled by a webhook sender that hangs up early.

One default to set: without `keepalive_timeout` the runner's `RequestHandler` keeps idle connections for 3630 seconds, while `run_app` uses 75 (`aiohttp/web_protocol.py`, `RequestHandler.__init__`; `aiohttp/web.py`, `run_app`). Pass `AppRunner(app, keepalive_timeout=75)`.

## Starlette 1.6.0 with uvicorn 0.52.4

Runs on the existing loop, with a signal catch. The uvicorn index page says "If you'd like to run Uvicorn from an already running async environment, use `uvicorn.Server.serve()` instead" and shows `await server.serve()` (https://github.com/Kludex/uvicorn/blob/master/docs/index.md, rendered at https://uvicorn.dev/); `Config` and `Server` are in `uvicorn.__all__`. But `serve()` is `with self.capture_signals(): await self._serve(sockets)`, and `capture_signals`, on the main thread, does `signal.signal(sig, self.handle_exit)` for SIGINT and SIGTERM, restores the previous handlers when `serve()` returns, and then re-raises any signal it caught (`uvicorn/server.py`, `Server.serve`, `Server.capture_signals`; the comment reads "always use signal.signal, even if loop.add_signal_handler is available"). Inside `kinby serve` that means SIGTERM reaches uvicorn first, uvicorn shuts down, and only then is the signal re-raised into asyncio's handler and `stopping` set. Probe: the SIGINT and SIGTERM handlers differed before and after `serve()` started. The shutdown order still works out, by way of the re-raise; avoiding it means calling the undocumented `_serve()` or running `serve()` off the main thread, the two escapes the source offers. The changelog shows the handling has been reworked three times (0.13.0, 0.29.0, 0.35.0; https://github.com/Kludex/uvicorn/blob/master/docs/release-notes.md), so it is not a corner the project leaves alone. `Config.loop` is only consulted by `Server.run()`, so no loop policy or uvloop is set up under `serve()` (`uvicorn/server.py`, `Server.run`; `uvicorn/config.py`, `get_loop_factory`).

Ephemeral port. `--port` docs: "If set to 0, an available port will be picked" (https://github.com/Kludex/uvicorn/blob/master/docs/settings.md). `Server.startup()` creates the asyncio servers and sets `server.started = True` last; the bound port is `server.servers[0].sockets[0].getsockname()[1]`, which is what uvicorn's own startup log line reads (`uvicorn/server.py`, `Server.startup`, `_log_started_message`). There is no property, and uvicorn's tests poll `while not server.started: await asyncio.sleep(0.05)` after `create_task(server.serve())` (https://github.com/Kludex/uvicorn/blob/master/tests/utils.py, `run_server`). A bind failure calls `sys.exit(STARTUP_FAILURE)`, so `SystemExit` comes out of `await serve()`. Probe: worked, with the same polling.

HTTP and WebSocket. Starlette routes `WebSocketRoute` next to `Route` (https://github.com/Kludex/starlette/blob/main/docs/websockets.md), and uvicorn upgrades on the same listener (`uvicorn/protocols/http/h11_impl.py`, `_should_upgrade`), but only with `websockets` or `wsproto` installed: `ws="auto"` resolves to `websockets_sansio_impl.WebSocketsSansIOProtocol` if `websockets` imports, else to `wsproto_impl.WSProtocol`, else to `None`, and an upgrade request then logs "No supported WebSocket library detected. Please use \"pip install 'uvicorn[standard]'\", or install 'websockets' or 'wsproto' manually." and is served as plain HTTP (`uvicorn/protocols/websockets/auto.py`; `h11_impl.py`, `_unsupported_upgrade_warning`). The implementation moved recently: 0.50.0 (2026-07-04) made `websockets-sansio` the default and deprecated the legacy `websockets` implementation, 0.51.0 requires `websockets>=13.0` (release notes). Probe with `websockets` 17.1 installed: WebSocket echo worked on the same port.

Python 3.14. Starlette 0.48.0 (2025-09-13): "Add official Python 3.14 support" (https://github.com/Kludex/starlette/blob/main/docs/release-notes.md); uvicorn 0.38.0 (2025-10-18): "Support Python 3.14" (release notes). Both carry the 3.14 classifier and `Requires-Python: >=3.10` (installed `METADATA`).

Footprint, license, maintenance. Starlette requires `anyio` (which pulls `idna`); uvicorn requires `click` and `h11`; WebSockets add `websockets` (BSD-3) or `wsproto` (MIT). All pure Python. Starlette and uvicorn are BSD-3-Clause, anyio and h11 MIT, click BSD-3 (installed `METADATA`). Resolved set: six packages plus a WebSocket library. Both are maintained by Marcelo Trylesinski; the `encode` repositories redirect to `Kludex`. Twenty-one Starlette releases and twenty-four uvicorn releases in the last twelve months, Starlette 1.0.0 on 2026-03-22, latest 1.6.0 on 2026-08-08 and uvicorn 0.52.4 on 2026-08-18 (release notes; https://pypi.org/project/starlette/, https://pypi.org/project/uvicorn/).

Raw body. `Request.body()` returns `bytes` joined from `stream()`, which concatenates `http.request` messages until `more_body` is false (`starlette/requests.py`). uvicorn's h11 and httptools paths hand the app the de-chunked entity body and decode nothing else (`uvicorn/protocols/http/h11_impl.py`, `handle_events`). Probe: byte-for-byte.

Body cap. uvicorn has none: its limits are `h11_max_incomplete_event_size` (request line and headers), `limit_max_requests` and `limit_concurrency`; nothing measures a body (`uvicorn/config.py`, `Config.__init__`). Starlette 1.6.0 (2026-08-08) added one: "Add `max_body_size` to `Starlette` and route classes" (release notes). `Starlette(max_body_size=...)` installs `RequestBodyLimitMiddleware`, which refuses on `Content-Length` before reading, otherwise counts `http.request` bytes and refuses when the total passes the limit, answering `PlainTextResponse("Content Too Large", status_code=413)` (`starlette/middleware/body_limit.py`; https://github.com/Kludex/starlette/blob/main/docs/middleware.md). The default is `None`, no limit. uvicorn reads and discards the rest of a refused body and keeps the connection alive (`h11_impl.py`: data after `h11.DONE` is skipped, `EndOfMessage` starts the next cycle). Probe: with `max_body_size=1024`, 2 KiB bodies with `Content-Length` and chunked both got 413 "Content Too Large"; a hand-written cap in the handler behaved the same way on 3 MiB bodies and the connection was reused for a following 200. So the cap is one month old in Starlette but it is a constructor argument, as in aiohttp.

Start and stop. `Server.main_loop` is `while not should_exit: await asyncio.sleep(0.1); should_exit = await self.on_tick(counter)`, and `Server.shutdown` begins with an unconditional `await asyncio.sleep(0.1)` before closing connections and waiting up to `timeout_graceful_shutdown` (default `None`, unbounded) for in-flight requests (`uvicorn/server.py`). Setting `server.should_exit = True` is therefore answered within two ticks. Probe: 158 ms from `should_exit` to `serve()` returning with one idle keep-alive connection open. uvicorn's tests skip the tick by calling `await server.shutdown()` and cancelling the `serve()` task (`tests/utils.py`). `lifespan="off"` skips the ASGI lifespan handshake, which kinby does not need because the runtime already owns startup.

## Hypercorn 0.18.0

Runs on the existing loop, and of the ASGI servers it does so with the least ceremony. `hypercorn.asyncio.serve(app, config, *, shutdown_trigger=None, mode=None)` documents "It is assumed that the event-loop is configured before calling this function" and "shutdown_trigger: This should return to trigger a graceful shutdown" (`src/hypercorn/asyncio/__init__.py`; https://hypercorn.readthedocs.io/en/latest/how_to_guides/api_usage.html). In `worker_serve` the whole signal-handler block sits under `if shutdown_trigger is None:`, so passing `stop_event.wait` installs nothing (`src/hypercorn/asyncio/run.py`, `worker_serve`). Probe: handlers unchanged.

Ephemeral port: not readable. `serve()` creates its sockets internally and returns nothing; the bound address only appears in a log line. The documented way round is to bind a socket yourself and pass `config.bind = ["fd://<fileno>"]` (https://hypercorn.readthedocs.io/en/latest/how_to_guides/configuring.html; `src/hypercorn/config.py`, `_create_sockets`), or to call the undocumented `worker_serve(sockets=...)`. Probe: the `fd://` route worked, and Hypercorn wraps the same descriptor in a second socket object, so the caller has to avoid a double close.

HTTP and WebSocket: yes, `wsproto` is a hard dependency and the h11 protocol upgrades in place (`src/hypercorn/protocol/h11.py`). Probe: echo worked.

Python 3.14: 0.18.0 changelog "Drop Python 3.8, 3.9 and support 3.13, 3.14"; classifier present (https://github.com/pgjones/hypercorn/blob/main/CHANGELOG.rst; installed `METADATA`).

Footprint, license, maintenance. Requires `h11`, `h2`, `priority`, `wsproto`, which pull `hpack` and `hyperframe`; all pure Python, MIT (installed `METADATA`). The concern is cadence: 0.18.0 on 2025-11-08 is the only release in the last twelve months, after an eighteen-month gap from 0.17.3 (https://pypi.org/project/hypercorn/#history). One maintainer.

Raw body: same ASGI story as Starlette; byte-for-byte in the probe. Body cap: none for ASGI. The only size settings are `h11_max_incomplete_size` (request line and headers), the HTTP/2 frame and header limits, `websocket_max_message_size` and `wsgi_max_body_size`, and the last applies only to the WSGI wrapper (`src/hypercorn/config.py`). Starlette's `max_body_size` would supply it. Probe with a handler-level cap: the `Content-Length` refusal worked and the connection was reused; the chunked refusal closed the connection on the client side (Windows; not reproduced elsewhere).

Start and stop: awaitable and prompt. When the trigger returns, listeners close, in-flight tasks get `graceful_timeout` (default three seconds), the lifespan shutdown is awaited, and `serve()` returns (`src/hypercorn/asyncio/run.py`, `worker_serve`). Probe: 1 ms. Hypercorn always runs the ASGI lifespan handshake and logs "ASGI Framework Lifespan error, continuing without Lifespan support" when the app does not implement it (`src/hypercorn/asyncio/lifespan.py`).

## Granian 2.8.2

Rejected on the first requirement. Granian is a Rust server (tokio, hyper) that spawns worker processes and owns the process; the README's programmatic examples are loop factories and hooks. There is an embedded variant, `granian.server.embed.Server`, whose `serve()` logs "Embedded server is experimental!" and runs workers "as AsyncIO tasks" (README; `granian/server/embed.py`). What that means in the source is that the ASGI app callbacks are scheduled onto the host loop while accepting and parsing happen on a spawned OS thread with its own tokio runtime (`src/serve.rs`). The bound port of a `port=0` bind is recorded in Rust (`src/net.rs`, `ListenerSpec.resolved_port`) but has no Python accessor, and no request body limit is exposed (`granian/http.py`, `granian/cli.py`). Active project (twenty releases in twelve months, BSD-3-Clause, 3.14 classifier), wrong shape for a server that has to live inside someone else's loop.

## Comparison

| On the existing loop, no signal handlers | yes | replaces SIGINT/SIGTERM while serving | yes with `shutdown_trigger` | experimental embed, I/O on Rust threads |
| Ephemeral port read back | `TCPSite.port` | `server.servers[0].sockets[0]` after polling `started` | pre-bind and `fd://` | no accessor |
| WebSocket, same port | built in | needs `websockets` or `wsproto` | built in | yes |
| Python 3.14 | since 3.13.0, Oct 2025 | since Sep and Oct 2025 | since 0.18.0, Nov 2025 | yes |
| Packages installed | 9 | 7 with `websockets` | 7 | 2 |

| Releases, last 12 months | 10 | 21 and 24 | 1 | 20 |
| Raw body | `request.read()` | `request.body()` | `request.body()` | ASGI |
| 1 MiB cap with 413 | `client_max_size`, default 1 MiB | `max_body_size`, since Aug 2026 | app code, or Starlette's | none |
| Stop | awaitable, immediate | 100 ms tick, 158 ms measured | awaitable, immediate | `stop()` |

## Recommendation

aiohttp, through `AppRunner` and `TCPSite`, with `client_max_size` at its default, `handle_signals` at its default `False`, `keepalive_timeout=75`, and `shutdown_timeout` short enough that `kinby serve` still stops promptly under a hung sender. `kinby serve` builds the `Application` before boot, starts the site after the runtime is up, and awaits `runner.cleanup()` in the same `finally` that stops the routine. Tests bind `TCPSite(runner, "127.0.0.1", 0)` and read `site.port`. The WebSocket socket lands later as a GET route on the same application, closed from `on_shutdown` with `WSCloseCode.GOING_AWAY` as the docs show.

What kinby gives up: seven ASGI-portable pure-Python packages become nine with five compiled, and the WebSocket server code is aiohttp-specific. What it avoids: a private `_serve()` call or a second thread to keep uvicorn's hands off the signal handlers `_serve_instance` owns, a 100 ms tick on every stop, a WebSocket library chosen and pinned separately, and a body cap that is one release old. Starlette with uvicorn is the runner-up and a fair choice if the server effort later decides ASGI portability matters more than the seam; Hypercorn would be the cleaner ASGI host for this process if its release pace were not one version in eighteen months.
