# Research: shipping a kinby package as a Python distribution

Wayfinder ticket: jorgesolerrr/kinby #213, child of the map "kinby next: hub, packages, web app, usage map" (#211). Date: 2026-09-11.
Question: how a Python distribution carries an instance template (`SYSTEM.md`, `permissions.toml`, `routines/`, `skills/`, `tools/`, manifest defaults, a name, description, and icon) and exposes it to kinby; how uv installs it into the runtime image and pins it per instance; what `kinby init --package <name>` copies versus references, and what a later package update means for a seeded instance.

Doc versions read: Python 3.14 standard library docs, uv docs current with uv 0.12.13, Hatch docs `latest` (hatchling 1.32.0), packaging.python.org `latest`, Copier docs `stable`.

## Short answer

1. A kinby package is an ordinary distribution built by hatchling from a `src/` layout: `kinby-coder` on PyPI, `kinby_coder` as the import name. Everything under `src/kinby_coder/` ships in the wheel with no build configuration, including a `template/` directory with no `__init__.py`, because hatchling's default selection for a `src/<name>/__init__.py` project is the whole directory.
2. Discovery stays on entry points; files come through `importlib.resources`. Tools and skills keep the existing `kinby.tools` and `kinby.skills` groups from ADR 0010 and ADR 0024, so a package is a plugin the way `kinby.plugins.defaults` already is. One new group, `kinby.packages`, exports a `Package` record (name, description, icon, template directory). The template path is `files("kinby_coder") / "template"`, which is a real `pathlib.Path` for any wheel pip or uv installed.
3. Install at image build, never at container start: `uv pip install --system "kinby-coder==1.2.0"` (or a `git+https://...@<tag>` requirement) as one layer on top of the kinby image. The instance manifest records the package name and version; the hub turns that pin into an image tag. Container start stays offline and restart-safe, which is what `restart: unless-stopped` and the catch-up scan assume.
4. `kinby init --package coder` copies the files the user owns and edits (`SYSTEM.md`, `RECAP.md`, `permissions.toml`, `routines/<name>/ROUTINE.md` plus its one-line `run.py`, `memory/profile.md`, and manifest defaults merged into `kinby.toml`) and references what is code (tools, skills, the code step's implementation) through the installed package. It writes `[package] name` and `version` into `kinby.toml`, the way Copier records `_src_path` and `_commit`.
5. A later package update changes the referenced parts at the next turn boundary after the image is rebuilt, and leaves the copied parts alone. kinby compares the recorded version with the installed one and warns. A three-way merge of the copied files (Copier's `update` model) is a later command, not part of the first cut.

## What the repo does today

- `pyproject.toml` declares `[project.entry-points."kinby.tools"] defaults = "kinby.plugins.defaults:TOOLS"` and `[project.entry-points."kinby.skills"] defaults = "kinby.plugins.defaults:SKILLS"`. Build backend: hatchling, no `[tool.hatch]` section.
- `src/kinby/plugins/defaults/__init__.py` exports `TOOLS = (read, write, edit, grep, glob, bash)` and `SKILLS: Path = Path(__file__).parent / "skills"`. The `skills/write-routine/SKILL.md` under it ships in the wheel with zero configuration, which already proves the hatchling rule below.
- `src/kinby/plugins/registry.py` loads `entry_points(group="kinby.tools")`, requires each to load to a `Sequence[Tool]`, skips the `defaults` entry when it belongs to the `kinby` distribution and the manifest says `[tools] defaults = false`, and drops packaged tools that two packages both export. `src/kinby/plugins/skills.py` does the same for `kinby.skills`, requiring a `Path` that `is_dir()`. Both keep other packages available when one export is broken.
- `src/kinby/plugins/routines.py` reads routines only from `<instance>/routines/*/ROUTINE.md`. There is no packaged tier for routines. A routine's code step is either `run.py` beside the file (compiled from its path, must define one tool) or `run: <tool name>` resolved from the turn's tool snapshot.
- `instances/coder/` is the instance that becomes the first package: `kinby.toml` (models, workspace source, conventions, serve, budgets, prices), `SYSTEM.md` (four lines), `RECAP.md`, `permissions.toml` (mode, ceiling, a bash denylist), `skills/unslop/SKILL.md`, `routines/implement-ready-issue/ROUTINE.md` (schedule, arguments, an HMAC signal) and `run.py`, which is one line: `from kinby.factory import implement_ready_issue`. The factory itself is about 1,400 lines under `src/kinby/factory/`, in core. Moving the coder to its own repository moves that code with it.
- `src/kinby/instance/init.py` writes the starter instance as string literals. `kinby init` takes a directory and `--model`; there is no template copying and no package flag.
- `Dockerfile`: `python:3.14-slim`, copies uv 0.8.17 in, then `pip install --no-cache-dir .` of the kinby checkout. uv is in the image for the coding workspace, not for kinby's own install. `docker/update.sh` fast-forwards the checkout to `origin/main` and rebuilds; `docker/entrypoint.sh` prepares the mounted instance and execs `kinby`.

## Entry points versus `importlib.resources`

They answer different questions, so a package uses both.

**Entry points answer "which installed distributions are kinby packages, and what do they export".** The specification allows a group named `kinby.packages` (groups match `^\w+(\.\w+)*$`) and a value of the form `importable.module:object.attr` ([entry points specification](https://packaging.python.org/en/latest/specifications/entry-points/)). The value is any importable attribute: `EntryPoint.load()` is `import_module` followed by `getattr` down the attribute path ([CPython 3.14 `importlib/metadata/__init__.py`](https://github.com/python/cpython/blob/3.14/Lib/importlib/metadata/__init__.py)); only the `console_scripts` group requires a callable. That is why `defaults = "kinby.plugins.defaults:SKILLS"` can export a `Path` today, and why a `kinby.packages` entry can export a frozen dataclass. `EntryPoint.dist` gives the owning distribution, so `entry_point.dist.name` and `entry_point.dist.version` are the package's PyPI name and installed version with no extra bookkeeping ([importlib.metadata, Entry points](https://docs.python.org/3.14/library/importlib.metadata.html#entry-points)). `entry_points()` walks every distribution on `sys.path` on each call and caches only per-path directory listings, so kinby should call it once per process and keep the result, which the tool registry already does at construction.

**`importlib.resources` answers "where are this package's files".** `files(anchor)` takes a package name or module and returns a `Traversable`; "The resources may be contained directly in a package, within a subdirectory contained in that package, or adjacent to modules outside a package" ([importlib.resources, 3.14](https://docs.python.org/3.14/library/importlib.resources.html)). Subdirectories need no `__init__.py`; support for directories inside namespace packages landed in the backport (`importlib_resources` 3.2.0, 6.1.0, 6.1.2, [NEWS](https://github.com/python/importlib_resources/blob/main/NEWS.rst)). `as_file()` turns a `Traversable` directory into a `pathlib.Path` inside a context manager and cleans up a temporary copy when the package came from a zip ([`as_file`](https://docs.python.org/3.14/library/importlib.resources.html#importlib.resources.as_file), directory support since 3.12).

**Why `Path(__file__).parent` works and when to stop relying on it.** Installing a wheel means unpacking the archive into `site-packages` ([binary distribution format, installing a wheel](https://packaging.python.org/en/latest/specifications/binary-distribution-format/#installing-a-wheel-distribution-1-0-py32-none-any-whl)), so pip and uv installs put the package on disk as ordinary files, and `files("kinby_coder")` returns a plain `pathlib.Path` (CPython's `FileReader.files()` in [`importlib/resources/readers.py`](https://github.com/python/cpython/blob/3.14/Lib/importlib/resources/readers.py)). Setuptools' data-files guide still says `__file__` "isn't compatible with PEP 302-based import hooks, including importing from zip files" and recommends `importlib.resources` ([Data files support](https://setuptools.pypa.io/en/latest/userguide/datafiles.html#accessing-data-files-at-runtime)). The practical rule for kinby: export `files(__package__) / "template"`; the loaders keep checking `isinstance(root, Path)` because kinby's tool loader compiles `.py` files from a path and the routine loader globs a directory, neither of which works on a zip-backed `Traversable`. A zipped kinby is not a supported deployment; a package that trips the check gets the same warning a broken export gets today.

**Not chosen: a data directory outside the package.** Hatchling's `shared-data` maps files under `sys.prefix` ([wheel builder options](https://hatch.pypa.io/latest/plugins/builder/wheel/#options)); `importlib.resources` cannot reach them and there is no clean way to find `sys.prefix` data for one distribution. Keep the template inside the import package.

## Package data under hatchling

- **Default selection ships the whole package directory.** When no file selection is set, hatchling looks for `<NAME>/__init__.py`, then `src/<NAME>/__init__.py`, then `<NAME>.py`, then `<NAMESPACE>/<NAME>/__init__.py` ([wheel builder, default file selection](https://hatch.pypa.io/latest/plugins/builder/wheel/#default-file-selection)). A hit on the `src` heuristic is `packages = ["src/<name>"]` in the source ([`hatchling/builders/wheel.py`](https://github.com/pypa/hatch/blob/master/backend/src/hatchling/builders/wheel.py)), and `packages` "is semantically equivalent to `only-include`", which selects a directory and everything under it ([build configuration, packages](https://hatch.pypa.io/latest/config/build/#packages)). Nothing filters by extension or by the presence of `__init__.py`. So `src/kinby_coder/template/routines/implement-ready-issue/ROUTINE.md` ships as long as git tracks it. The docs never state "all files under the package are included" as a sentence; it follows from the selection rules, and kinby's own `write-routine` skill demonstrates it.
- **Exclusion follows the VCS.** Hatch "will respect the first `.gitignore` or `.hgignore` file found in your project's root directory or parent directories" ([VCS](https://hatch.pypa.io/latest/config/build/#vcs)); `artifacts` force-includes ignored files, `exclude` removes tracked ones. Consequence: a template must not depend on ignored files. Ship `.env.example`, never `.env`; `kinby init` writes the instance `.gitignore` itself from `kinby.instance.layout`, so the template needs none.
- **No `MANIFEST.in`, no `__init__.py` requirement below the top level.** The build docs' vocabulary is `include`, `exclude`, `only-include`, `packages`, `artifacts`, `force-include`, `sources`; `MANIFEST.in` appears only on the "Why Hatch" page as the setuptools mechanism hatchling replaces ([Why Hatch](https://hatch.pypa.io/latest/why/)). `force-include` maps a path from anywhere on disk into the wheel if a package ever wants the template outside `src/` ([forced inclusion](https://hatch.pypa.io/latest/config/build/#forced-inclusion)); not needed here.
- **Empty directories do not ship.** Git does not track them and wheels are file archives. `memory/graph/`, `.state/`, `workspace/`, `tools/` with no files: `kinby init` creates them, as it does today.
- **Python files under the template are data, not modules.** `template/routines/<name>/run.py` and `template/tools/*.py` are copied into the instance and compiled from their path by kinby's loader; the package never imports them. ruff and ty in the package repository will still see them, which is fine: they are one-line imports.

## Installing with uv: build time versus container start

**Commands that work.** `uv pip install "kinby-coder==1.2.0"`, `uv pip install "kinby-coder @ git+https://github.com/jorgesolerrr/kinby-coder@v1.2.0"` (tag, branch, or commit after `@`), a local wheel or directory ([pip interface, installing packages](https://docs.astral.sh/uv/pip/packages/#installing-a-package)). Inside a container "the system Python environment is safe to use", so `uv pip install --system` or `UV_SYSTEM_PYTHON=1` ([Docker guide](https://docs.astral.sh/uv/guides/integration/docker/)). For a project, `uv add git+https://... --tag v1.2.0` writes `[tool.uv.sources] kinby-coder = { git = "...", tag = "v1.2.0" }` ([Git dependencies](https://docs.astral.sh/uv/concepts/projects/dependencies/#git)), and the lock records the resolved commit (`?tag=v1.2.0#<sha>` in `uv.lock`, shown by uv's own [`lock_sdist_git` snapshot](https://github.com/astral-sh/uv/blob/main/crates/uv/tests/lock/lock.rs)); `uv pip compile` pins Git dependencies to a commit hash for the same reason ([cache, dependency caching](https://docs.astral.sh/uv/concepts/cache/#dependency-caching)). Outside a container, `uv tool install kinby --with kinby-coder` is the documented way to add a plugin distribution to a tool's private environment ([tools, including additional dependencies](https://docs.astral.sh/uv/guides/tools/#including-additional-dependencies)), and `uv tool upgrade kinby` refreshes it.

**Build time.** One `RUN uv pip install --system $KINBY_PACKAGES` layer on top of the kinby image. Deterministic, cached, and the container needs no network or registry credentials to start. The Docker guide's other advice applies as is: pin the uv image tag (`COPY --from=ghcr.io/astral-sh/uv:0.12.13`, the current tag), `UV_COMPILE_BYTECODE=1` for start time, `UV_LINK_MODE=copy` (already set), `--no-cache` or `UV_NO_CACHE` when no cache mount is used, `--mount=type=cache,target=/root/.cache/uv` when one is. Switching kinby's own install from `pip install .` to `uv sync --locked --no-dev` in the same Dockerfile would make kinby's dependencies follow `uv.lock` instead of a fresh resolution per build; that is a separate, small change.

**Container start.** `uv pip install --system` from the entrypoint, or `uv run --with kinby-coder==1.2.0 kinby serve` (a `--with` layer is "a separate, ephemeral environment" on top of the project, [uv run reference](https://docs.astral.sh/uv/reference/cli/#uv-run)). This gives one image for every package, at the cost of a network fetch on every restart, a uv cache volume "on the same file system as the Python environment" to make it fast ([cache](https://docs.astral.sh/uv/concepts/cache/)), and a new failure mode: an install that fails at boot leaves the instance down, and the box reboots at 04:30 UTC for security updates (ADR 0030, accepted risks). The hub creates containers per instance and already owns image builds, so the flexibility is not needed there.

**Pinning per instance.** The instance owns the pin: `[package] name = "kinby-coder"` and `version = "1.2.0"` in `kinby.toml` (or `source = "git+https://...@<sha>"` for an unreleased package). The hub derives the image from the pin: build the kinby image once per kinby version, then a derived image per distinct package set, tagged by the pin (`kinby:0.3.0-coder-1.2.0`, or a hash of the requirement list). Two instances on the same pin share an image; bumping one instance's pin builds one new image and restarts one container. This is the same rhythm as `docker/update.sh` today, one level down. Package discovery beyond the curated list stays parked on the map; PyPI name normalization means `kinby-coder`, `kinby_coder`, and `Kinby.Coder` are one project ([name normalization](https://packaging.python.org/en/latest/specifications/name-normalization/)), so the curated list can store the canonical dashed name and the entry-point name.

## What `kinby init --package <name>` copies and what it references

The rule: **the user owns and edits what is copied; the package owns and updates what is referenced.** kinby already draws this line for skills in ADR 0024: `write-routine` lives in the package "so the routine format updates with kinby instead of freezing in a file copied by `kinby init`", and an instance file shadows a packaged one silently.

| Template item | Copy or reference | Why |
|---|---|---|
| `kinby.toml` defaults (`[models]`, `[workspace]` source and conventions, `[serve]`, `[budgets]`, `[prices]`, `[feedback]`, `[memory]`) | Copy, merged into the manifest `init` writes, plus `[package] name` and `version` | The manifest is the instance's identity; the user changes models and budgets. Recording the pin is what makes a later update possible (Copier records `_src_path` and `_commit` for the same reason, [Copier answers file](https://copier.readthedocs.io/en/stable/configuring/#the-copier-answersyml-file)). |
| `SYSTEM.md`, `RECAP.md` | Copy | The behavior prompt is "the instance's own instructions"; the instance tool edits it; the prompt version hash groups turns by "the prompt the user wrote". A referenced prompt would change under the user without a turn boundary they chose. |
| `permissions.toml` | Copy | Mode, ceiling, and the denylist are the instance's ceiling; the gate reads the instance file. |
| `routines/<name>/ROUTINE.md` | Copy | The routine loader reads the instance directory only; `enabled`, `schedule`, `arguments`, and `mode` are user settings; the failure policy disables a routine by rewriting the file. |
| `routines/<name>/run.py` | Copy the one-line import; the implementation stays in the package | Keeps the code step out of the model's tool list (a code step is "a tool never offered to the model"), and the implementation updates with the package. The alternative, `run: <tool name>` resolved from the packaged tools, makes the code step a model-visible tool; not worth it. |
| `tools/*.py` | Reference through `kinby.tools` | Package tools are importable modules with tests and types; the entry-point tier already exists, and an instance file shadows a packaged tool when the user wants to replace one. The template's `tools/` directory stays empty except for the README `init` writes. |
| `skills/<name>/SKILL.md` | Reference through `kinby.skills` | Same reasoning as ADR 0024; the coder's `unslop` skill updates with the package; an instance skill shadows it. |
| `memory/profile.md` | Copy (a starter, usually the placeholder) | Memory is the instance's. |
| name, description, icon | Read from the `kinby.packages` record, shown by the suggestion card and `kinby instance show` | Presentation, never copied. |
| `.env.example` | Copy | Names the secrets the routines' signals expect (`GITHUB_WEBHOOK_SECRET`, `GH_TOKEN`). |

**Resolving `<name>`.** Match the entry-point name (`coder`) first, then the normalized distribution name (`kinby-coder`), from `entry_points(group="kinby.packages")`. The package must be installed in the environment running `kinby init`; in the hub flow that is the derived image, so the hub runs `kinby init --package coder /instance` inside a container from that image before it starts `serve`. Two installed packages exporting the same entry-point name get the duplicate warning the tool loader already gives.

**The record in the manifest.**

```toml
[package]
name = "kinby-coder"
version = "1.2.0"
```

## What a later package update means for a seeded instance

An update is a new pin in `kinby.toml`, a rebuilt image, and a restart. After it:

- **Referenced parts move at once.** Tools, skills, and the code step's implementation come from the installed distribution, so the next turn boundary loads the new versions (ADR 0010 rescans at turn boundaries; the entry-point set is read at process start, which a restart is). No instance file changes. A new tool argument must keep a default, since the copied `ROUTINE.md` passes the old `arguments`; the pipeline function already takes its settings as keyword arguments with defaults, which is the right contract for a package to promise.
- **Copied parts stay.** `SYSTEM.md`, `permissions.toml`, `ROUTINE.md` keep the user's edits and the old template text. kinby sees `[package] version` differs from `entry_point.dist.version` and reports it as a warning on `instance show` and at boot: "seeded from kinby-coder 1.2.0, installed 1.3.0". Nothing is rewritten under the user.
- **A merge is a later command.** Copier's `update` regenerates the project at the recorded template version, diffs that against the real project, regenerates at the new version, and re-applies the diff, with git-style conflict markers by default ([Copier, updating a project](https://copier.readthedocs.io/en/stable/updating/)). kinby can do the same with the two template directories and `git merge-file`, because the old template is one `uv pip install kinby-coder==1.2.0` away and the new one is installed. Cookiecutter has no update command at all ([Cookiecutter usage](https://cookiecutter.readthedocs.io/en/stable/usage.html)), which is what an instance without a recorded pin would be reduced to. Record the pin now; build `kinby package update` when the second package exists and a real diff shows what the merge must handle.

## Comparison with the `defaults` package

| | `kinby.plugins.defaults` today | A kinby package |
|---|---|---|
| Distribution | part of `kinby` | its own (`kinby-coder`), own repository, depends on `kinby` |
| Tools | `kinby.tools` entry point, `TOOLS` tuple | same group, same shape |
| Skills | `kinby.skills` entry point, `SKILLS: Path` | same group, `files(__package__) / "template" / "skills"` or a sibling `skills/` directory |
| Routines, prompt, permissions, manifest defaults | none | `template/` directory, copied by `kinby init --package` |
| Identity | the `defaults` entry-point name and the `kinby` distribution check in the loaders | a `kinby.packages` entry point exporting name, description, icon, and the template path; version from `EntryPoint.dist` |
| Switch off | `[tools] defaults = false` | uninstall, or shadow a tool or skill with an instance file |

The `defaults` special case in both loaders (skip the entry named `defaults` when its distribution is `kinby`) stays as it is; a package is just another distribution to those loaders.

## Recommendation

1. **Shape.** `kinby-coder` is a hatchling `src/` layout distribution depending on `kinby`. `src/kinby_coder/` holds the factory code moved out of `src/kinby/factory/`, `tools.py` exporting `TOOLS`, a `skills/` directory exporting `SKILLS`, and `template/` with `kinby.toml` (defaults only, no `id`), `SYSTEM.md`, `RECAP.md`, `permissions.toml`, `routines/implement-ready-issue/ROUTINE.md` and `run.py`, `memory/profile.md`, `.env.example`. No `[tool.hatch]` configuration.
2. **Exposure.** Three entry points: `kinby.tools`, `kinby.skills` (unchanged groups), and a new `kinby.packages` group whose value is a frozen `Package(name, description, icon, template)` with `template = files("kinby_coder") / "template"`. Loaders keep requiring a real `Path`. The curated suggestion cards in kinby carry the same three display fields plus the distribution name.
3. **Install.** At image build: `RUN uv pip install --system $KINBY_PACKAGES` as one layer over the kinby image, `KINBY_PACKAGES` built from the instance's `[package]` pin (`kinby-coder==1.2.0`, or `kinby-coder @ git+https://...@<sha>` before a release). The hub tags images by pin and rebuilds when a pin changes. Nothing installs at container start.
4. **`kinby init --package <name>`.** Copies the template files into the instance, merges manifest defaults with the generated `id`, writes `[package] name` and `version`, and creates the empty directories `init` creates today. Tools and skills are not copied; they load from the package.
5. **Updates.** Referenced parts follow the installed version at the next boundary; copied parts stay; a version mismatch is a warning, not a rewrite. `kinby package update` with a three-way merge waits for the second package.

## Open points for the spec

- Whether `[package]` should also let an instance switch a package's tools or skills off the way `[tools] defaults` does, or whether shadowing by instance file is enough. Shadowing looks sufficient.
- Whether the Dockerfile should move kinby's own install to `uv sync --locked --no-dev` at the same time. Small and independent; recommend yes when the package layer lands.
- The name of the derived image tag and where the hub keeps it (the instance registry row is the natural place; that is a hub research question).
