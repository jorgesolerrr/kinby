# Factories as code: Warp, GitHub Agentic Workflows and declarative agent pipelines

Wayfinder ticket: jorgesolerrr/kinby #517 (map #516). Date: 2026-10-03.
Question: how do Warp's agents-as-code and similar declarative agent pipelines define a pipeline (format, triggers, stages, agent per stage, state between stages, waiting on outside events, human gates, retries, authoring), and what could a kinby factory file borrow?

Systems compared: Warp Factories (Warp's agents-as-code, built on its Oz/Automation Platform), GitHub Agentic Workflows (`gh aw`), Archon, and goose recipes. Archon is the closest open-source analogue to a coding factory with a real DAG. Goose recipes are the simplest declarative format with a check-and-retry loop. All claims come from each project's own docs, read on the date above. A claim with no primary source is marked **unverified**.

## Short answer

1. **Warp Factories** is a directory of YAML and Markdown files (`factory.yaml`, `agents/<name>/agent.md`, `automations/<name>/automation.md`, runners, skills, webhooks, scorers). The files declare who the agents are and what starts them. They do not declare stages. The order of stages is prose in the foreman agent's instructions, and the foreman routes each work item at runtime. Each agent picks its harness (Warp Agent, Claude Code or Codex) and model.
2. **GitHub Agentic Workflows** is one Markdown file per workflow. Its frontmatter holds triggers, permissions, tools and the `engine` (a coding CLI: Copilot, Claude, Codex and others). `gh aw compile` turns it into a GitHub Actions lock file. Each run is a single agent job. Writes leave the agent as structured "safe outputs", and a separate permissioned job applies them. Chaining between workflows goes through Actions events or dispatch outputs.
3. **Archon** is a YAML DAG of typed nodes (`prompt`, `command`, `bash`, `script`, `loop`, `approval`, `wait`, `cancel`, `workflow`). Data moves between nodes as `$node.output`. Its runs are durable: they pause on approval or wait nodes, resume while skipping completed nodes, and can wait for a named event that has a deadline. Only AI nodes retry automatically. A deterministic node retries only if it opts in.
4. **Goose recipes** are one YAML file for one agent: a prompt, parameters, a structured `response` schema, `sub_recipes`, and a `retry` block that runs shell checks after the agent finishes and retries with reset history.
5. **For kinby**: keep the deterministic code step as the pipeline. Warp's prose foreman is the option ADR 0029 rejected (D4). The pieces worth borrowing are declarative, fail-closed trigger filters, a published schema plus an atomic "validate, then apply whole or keep the last good one" rule for instance files, the safe-outputs split, and Archon's opt-in retry and event-with-deadline rules. [What kinby could borrow](#what-a-kinby-factory-file-could-borrow) has the details.

## 1. Warp Factories (Warp's agents as code)

Warp's own name for the product is **Warp Factories**. It runs on the **Automation Platform**, which the docs also call Oz: the Oz CLI, the Oz API and the Oz web app ([factories overview](https://docs.warp.dev/factories/), [Oz CLI](https://docs.warp.dev/reference/cli/)).

**File format.** A factory is "a `factory.yaml` plus directories of agents, automations, runners, benchmarks, scorers, skills, and webhooks, versioned in a Git repository. The files are the source of truth" ([definition syntax](https://docs.warp.dev/factories/factory-as-code/)). Each resource takes its name from its path (`agents/reviewer/agent.md` is the agent `reviewer`). Only `factory.yaml` and one agent are required. `factory.yaml` names the factory, lists `repositories`, and sets `agentDefaults` (model or harness, runner, secrets, MCP servers, worker host). An `agent.md` holds YAML frontmatter (`description`, `agentType`, overrides of the defaults) and a Markdown body that is "the agent's prompt: the durable instructions for its role". An `automation.md` holds `enabled`, `agent` (defaults to the foreman), `triggers`, optional execution overrides, and a body that is "the prompt each run starts with" ([same page](https://docs.warp.dev/factories/factory-as-code/#automationsnameautomationmd)). Skills are `SKILL.md` directories, either factory-wide or per agent.

**Triggers.** Each automation lists `triggers`, and each trigger is a `provider` and an `event` with an optional `filter`. The providers are GitHub (issue labeled, PR opened, review submitted, workflow run completed and more), GitLab, Linear, Jira, Slack, `schedule`/`cron_fired` (cron in UTC), `webhook`/`received`, and `factory`/`work_item_stage_changed` ([triggers](https://docs.warp.dev/factories/factory-as-code/#triggers)). The filter rules: every key must match, any listed value within a key matches, and an omitted key matches everything. Webhook triggers add a JSON payload pattern with `in`, `not_in` and `exists`. "A filter that can't be evaluated never matches", so a broken filter keeps the automation silent instead of firing it ([automations](https://docs.warp.dev/factories/automations/#payload-filter-reference)). Filters decide when work starts, not what an agent can reach. Access comes from the provider authorization ([automations](https://docs.warp.dev/factories/automations/#filters-dont-control-access)). Webhook files declare `authMode` (`token`, `url_token`, `signature` with a named provider scheme), a `secretName`, and a `deliveryIdHeader` for deduplication ([webhooks](https://docs.warp.dev/factories/factory-as-code/#webhooksnameyaml)).

**Stages and the agent per stage.** Every factory has one foreman plus default triage, spec, implement and review agents (`agentType` `FOREMAN`, `TRIAGE`, `SPEC`, `IMPLEMENT`, `REVIEW`, `VERIFY`, `CUSTOM`). The docs say "these are responsibilities, not a fixed pipeline". The foreman "picks the shortest path that still meets your quality policy", skipping stages or sending work back ([factory agents](https://docs.warp.dev/factories/factory-agents/), [how factories work](https://docs.warp.dev/factories/how-factories-work/)). So the pipeline graph lives in the foreman's prompt, not in a schema. Each agent can run on its own harness: `harness: {type: oz | claude | codex, model, reasoningLevel, auth}`. `model:` alone is shorthand for the Warp Agent harness. Claude Code and Codex credentials come from a managed secret or a self-hosted worker's environment ([agentDefaults.harness](https://docs.warp.dev/factories/factory-as-code/#agentdefaultsharness)). The docs advise a review agent on "a different model or harness from the implement agent, so the two don't share blind spots" ([factory agents](https://docs.warp.dev/factories/factory-agents/#choose-models-and-harnesses-per-agent)).

**Work and state between stages.** A work item "keeps its identity from intake to handoff". The foreman holds one conversation per work item and "continues existing agent conversations instead of starting new ones" ([how factories work](https://docs.warp.dev/factories/how-factories-work/)). Implement continues the spec agent's branch and draft PR ([factory agents](https://docs.warp.dev/factories/factory-agents/#implement)). Under a factory, parent and child runs talk over a durable message bus with per-agent inboxes. A finished child "is still addressable by its agent ID and will wake up to handle follow-up instructions" ([orchestration](https://docs.warp.dev/platform/orchestration/)). Work items, runs and metrics are never written to the definition files ([definition syntax](https://docs.warp.dev/factories/factory-as-code/#where-the-definition-lives)).

**Waiting on outside events.** There is no wait primitive in the files. A later event re-enters the work: "a reply in the same thread, issue, or pull request continues that work item instead of starting a new one, and repeated event deliveries don't create duplicates" ([connect your factory](https://docs.warp.dev/factories/connect-your-factory/)). Automations on `pull_request_review_submitted`, `workflow_run_completed` (filterable by `conclusions`) or `check_suite_completed` start the follow-up ([GitHub integration](https://docs.warp.dev/factories/integrations/github/)).

**Human gates.** There are three by default: spec approval, answering questions, and merging. "The first two are workflow policy, written into the foreman's instructions". Merging is enforced by the repository's branch protection, and "changing what an agent is told to do doesn't change what it's able to do" ([factory agents](https://docs.warp.dev/factories/factory-agents/#human-decision-points-and-permissions)). A run can also reach `BLOCKED`, which means waiting on a command approval or permission ([orchestration](https://docs.warp.dev/platform/orchestration/#run-state-transitions)).

**Retries and failure.** Run states are `INPROGRESS`, `SUCCEEDED`, `FAILED`, `BLOCKED`, `ERROR` and `CANCELLED`. The parent decides whether to "send a follow-up, spawn a replacement, or finish" ([orchestration](https://docs.warp.dev/platform/orchestration/#run-state-transitions)). A runner can keep a failed session open 1 to 60 minutes for inspection (`failureSessionRetentionMinutes`). **Unverified:** the factory docs I read describe no declarative per-stage retry or timeout key. Retry is the foreman's judgement. Scorers and Self-improvement turn repeated failures into proposed follow-up PRs ([how factories work](https://docs.warp.dev/factories/how-factories-work/#how-the-factory-improves-itself)).

**Authoring and editing.** A factory is edited in two ways. The Warp-managed way is a web app that validates and commits each save. The GitHub way makes a repository the only path: a `warp/factory-config` PR check reports problems by file and line and summarizes what a merge will create, update or delete. "A definition that fails validation never partially applies, and the factory keeps running its last valid definition" ([definition syntax](https://docs.warp.dev/factories/factory-as-code/#pull-request-checks)). Warp publishes a JSON Schema per file kind and a standalone `validate_factory_files.py`. Its agent has a `factory-files` skill that validates before it opens a PR ([JSON Schema](https://docs.warp.dev/factories/factory-as-code/#json-schema)).

## 2. GitHub Agentic Workflows

**File format.** Workflows are "Markdown with YAML frontmatter" that run AI agents through GitHub Actions ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/about-github-agentic-workflows)). The frontmatter configures triggers, permissions, tools, the engine and `safe-outputs`. The Markdown body is the agent's instructions ([frontmatter](https://github.github.com/gh-aw/reference/frontmatter/)). `gh aw compile` produces a GitHub Actions lock file. "The markdown body ... loaded at runtime, takes effect on the next run". Frontmatter "is embedded at compile time and requires `gh aw compile`" after edits ([FAQ](https://github.github.com/gh-aw/reference/faq/)). `imports:` shares parts across workflows ([frontmatter](https://github.github.com/gh-aw/reference/frontmatter/)).

**Triggers.** `on:` takes standard Actions events (`issues`, `pull_request`, `pull_request_review`, `workflow_run`), plus fuzzy schedules (`daily`, `weekly on monday`), `slash_command`, `label_command` (removes the label after it fires), `stop-after`, `skip-if-match`/`skip-if-no-match` (a search query), `roles` and `forks` filters, and `manual-approval` ([triggers](https://github.github.com/gh-aw/reference/triggers/)).

**Stages and the agent per stage.** One workflow is one agent run. The compiler generates the activation, agent, threat-detection, safe-outputs and conclusion jobs ([how they work](https://github.github.com/gh-aw/introduction/how-they-work/)). `engine:` picks a coding CLI: `copilot`, `claude`, `codex`, `gemini`, `pi` or a custom engine, with `model`, `version`, `args` and `env` ([engines](https://github.github.com/gh-aw/reference/engines/)). Deterministic code runs in `pre-steps`, `steps`, `pre-agent-steps` and `post-steps`, or in custom `jobs:` that can gate the agent job through `jobs.agent.needs`/`if` ([frontmatter](https://github.github.com/gh-aw/reference/frontmatter/)).

**Work and state between stages.** The agent job runs read-only and "request[s] actions via structured output, while separate permission-controlled jobs execute those requests". Each output type (`create-pull-request`, `add-comment`, `add-labels`, `push-to-pull-request-branch`, `submit-pull-request-review`, `dispatch-workflow`, `call-workflow` and more) has a `max`. `noop`, `missing-tool` and `missing-data` are always available, and a staged mode previews outputs without side effects ([safe outputs](https://github.github.com/gh-aw/reference/safe-outputs/)). Workflows chain through `dispatch-workflow`, `call-workflow`, or a `workflow_run` trigger. State across runs lives in `cache-memory` (Actions cache, 7-day eviction) or `repo-memory` (a Git branch with no expiry) ([cache memory](https://github.github.com/gh-aw/reference/cache-memory/), [repo memory](https://github.github.com/gh-aw/reference/repo-memory/)).

**Waiting on outside events.** No in-run wait. A new run starts on `pull_request_review` or `workflow_run` ([triggers](https://github.github.com/gh-aw/reference/triggers/)). One caveat: PRs created with the default token do not trigger CI, a GitHub Actions rule against recursion ([FAQ](https://github.github.com/gh-aw/reference/faq/)).

**Human gates.** `manual-approval` on the trigger, or GitHub Environment protection rules on a custom safe-output job: "the job pauses until a designated reviewer approves, enforced by GitHub's infrastructure rather than workflow logic the agent could influence" ([FAQ](https://github.github.com/gh-aw/reference/faq/)).

**Retries and failure.** "gh-aw has no automatic retries, so each trigger produces one run". Loops are bounded with `max-turns` for Claude or `max-continuations` for Copilot ([FAQ](https://github.github.com/gh-aw/reference/faq/)). Inside a run, `engine.harness` sets `max-retries` (default 3), backoff and a `watchdog-timeout` ([engines](https://github.github.com/gh-aw/reference/engines/)). My reading is that this covers engine-process retries within one run, not re-running the workflow. `timeout-minutes` defaults to 20 ([frontmatter](https://github.github.com/gh-aw/reference/frontmatter/)). When a safe output fails, for example a PR blocked by protected files, the workflow can fall back to opening an issue ([safe outputs](https://github.github.com/gh-aw/reference/safe-outputs/)).

## 3. Archon

**File format.** Workflows live in `.archon/workflows/` in the repository or in `~/.archon/workflows/` ([repository](https://github.com/coleam00/Archon)). A workflow is YAML with a list of `nodes`. Each node has exactly one type: `command` (a packaged prompt file), `prompt`, `bash`, `loop`, `approval` or `cancel`, plus `script`, `wait`, `loop_group` and `workflow` (a sub-run) covered in the authoring guide ([docs, llms-full](https://archon.diy/llms-full.txt), "Nodes" and "Authoring Workflows").

**Triggers.** CLI (`archon workflow run`), the web UI, chat adapters (Slack, Telegram, Discord) and GitHub webhooks ([repository](https://github.com/coleam00/Archon)). Archon keeps triggers out of the workflow: "Schedules and event bindings are deployment configuration. They do not belong in workflow YAML." A binding picks the workflow, the run-as user, inputs, the host and an overlap policy ([docs](https://archon.diy/llms-full.txt), "Start workflows from schedules and GitHub events").

**Stages and the agent per stage.** `depends_on` forms a DAG, and nodes in the same layer run in parallel. `when:` expressions branch on upstream output, and `trigger_rule` sets join semantics. Provider and model can be overridden per node (Claude Code, Codex, OpenCode, Pi and others). `bash`/`script` nodes run without AI ([docs](https://archon.diy/llms-full.txt), "Authoring Workflows").

**Work and state between stages.** A node's stdout or AI result is `$nodeId.output`, and `output_format` validates JSON so that `$node.output.field` works ("a node that declares `output_format` but returns no schema-valid output fails"). Session continuity is explicit: `context: fresh | shared | {resume: <node>}` forks a named upstream node's session, and `persist_session` carries a role's session across separate runs ([docs](https://archon.diy/llms-full.txt), "Authoring Workflows", "Persistent Sessions Across Re-Runs"). Each run gets its own git worktree ([repository](https://github.com/coleam00/Archon)).

**Waiting on outside events.** A `wait:` node "records its condition in the workflow run, changes the run to `paused`, and returns the worker slot". The condition kinds are `duration_ms`, `until`, `event` and `attention` (an outside action for an operator). An `event` wait "requires `deadline_ms`" and completes with `status: expired` when the deadline passes, so "event waits cannot remain open forever". Signals go to one run through an authenticated `POST /api/workflows/runs/<id>/signal`, and duplicate or wrong-run signals do nothing. Restarting Archon preserves the wait ([docs](https://archon.diy/llms-full.txt), "Durable waits").

**Human gates.** An `approval:` node pauses the run. It is approved or rejected from a command, the CLI, chat, the web UI or the API. A plain chat message "is **not** an automatic approval". Without `on_reject`, a rejection cancels the run. With it, rework runs and the gate pauses again. `capture_response` exposes the reviewer's comment as `$gate.output`. `loop:` with `interactive: true` gives an iterate-until-approved gate ([docs](https://archon.diy/llms-full.txt), "Approval Nodes", [repository](https://github.com/coleam00/Archon)).

**Retries and failure.** AI nodes retry transient errors by default (2 retries, exponential backoff). "Deterministic nodes (`bash:`, `script:`) do **not** auto-retry ... This keeps side-effectful scripts (deploys, `gh` mutations, external CLIs) from being silently re-run". `retry:` on a `workflow:` node is not allowed, because a retry would orphan the first child run. `archon workflow resume <id>` re-runs a failed or paused run and skips every node that completed, feeding their cached outputs downstream. `always_run: true` opts a node out of that cache. `idle_timeout` kills a stalled node ([docs](https://archon.diy/llms-full.txt), "Retry Configuration", "Opting Out of Resume Caching").

## 4. Goose recipes

**Format.** One YAML or JSON file per recipe: `title`, `description`, `instructions` and/or `prompt`, `parameters`, `extensions` (MCP servers), `settings` (provider and model), `response.json_schema` (validated structured output), `sub_recipes` (each with `name`, `path`, `values`, `sequential_when_repeated`) and `retry` ([recipe reference](https://goose-docs.ai/docs/guides/recipes/recipe-reference/)).

**Retries.** `retry` has `max_retries`, shell `checks` that must exit 0, `on_failure` (a shell command) and timeouts. After the agent finishes, the checks run in order. On a failure, `on_failure` runs and the next attempt starts with the agent's message history reset ([recipe reference](https://goose-docs.ai/docs/guides/recipes/recipe-reference/)).

**Triggers.** None in the file. `goose schedule add --schedule-id … --cron … --recipe-source …` copies the recipe and runs it on cron ([CLI commands](https://goose-docs.ai/docs/guides/goose-cli-commands/)). Goose has no in-file human gate and no wait on outside events. Sub-recipes are its only composition.

## Side by side

| | Warp Factories | GitHub Agentic Workflows | Archon | Goose recipe |
|---|---|---|---|---|
| Unit | Directory of agents + automations | One Markdown workflow | One YAML DAG | One YAML recipe |
| Triggers in the file | Yes, per automation, with filters | Yes (`on:`) | No, deployment bindings | No, `goose schedule` |
| Stage order | Prose in the foreman's prompt | One agent job per run | Declared DAG | Single agent + sub-recipes |
| Agent per stage | Harness + model per agent | `engine` per workflow | Provider + model per node | `settings` per recipe |
| Deterministic code | Runner setup commands | `steps`, custom `jobs` | `bash`/`script` nodes | `checks`, `on_failure` |
| State between stages | Work item, foreman conversation, message bus | Safe outputs, cache/repo memory | `$node.output`, named session resume | Parameters to sub-recipes |
| Outside events | New event continues the work item | New run on the event | Durable `wait` with deadline | None |
| Human gate | Foreman policy; merge by branch protection | Environment protection, `manual-approval` | `approval` node, `on_reject` | None |
| Retries | Foreman's judgement (unverified) | None per run; engine-process retries | AI auto, deterministic opt-in, resume skips done | `retry` with shell checks |
| Validation | JSON Schema, PR check, atomic apply | `gh aw compile` | Loader validation | Schema on `response` |

## kinby today

A routine is `routines/<name>/ROUTINE.md`: frontmatter (`description`, `schedule`, `enabled`, `mode`, `catch_up`, `run`, `signal`, `arguments`, `steps`/`tokens`/`seconds`) and a prompt body, plus an optional `run.py` code step that runs first and may report no work (`src/kinby/plugins/defaults/skills/write-routine/SKILL.md`, `CONTEXT.md`). The coder in `kinby-code-factory` is two such routines. `implement-ready-issue` runs `pipeline.py`: it scans for the oldest eligible issue, prepares the `agent/` branch, implements with a coding client, optionally runs a review loop, runs the checks with one repair attempt, opens the PR, and returns a pipeline report. The model only comments that report. `babysit-pull-request` runs `babysit.py`, which re-derives everything from GitHub (threads, labels, checks) on every wake. Its wakes are an hourly cron plus signed GitHub deliveries. Stage settings live in the package's `package.yaml` (`implementation`, `review`, `babysitting`, `checks`, `skills`), validated by `FactoryConfig` (`src/kinby_code_factory/config.py`). ADR 0029 chose code over a model-driven pipeline (rejected D4). ADRs 0044 and 0046 turned review and babysitting off through settings without removing them.

The code step already holds kinby's stage graph, the way Archon's DAG and Warp's foreman prompt hold theirs. Pipeline state lives on GitHub, not in a paused run, like Warp's "new event continues the work item".

## What a kinby factory file could borrow

Ranked by fit. None of these needs a new pipeline language.

1. **Declarative, fail-closed trigger filters on `signal`.** Warp's `filter` (AND across keys, any value within a key, an omitted key matches all, `in`/`not_in`/`exists` on payload fields, never fires when it cannot evaluate) would replace the hand-written `payload_can_change_eligibility` and `signal_warrants_scan` checks. It would also avoid starting a turn for deliveries that cannot matter. A `signal.filter` with the same grammar fits next to `signal.auth`. The code step stays the authority for eligibility, as `CONTEXT.md` already requires ("a delivery can determine that no scan is needed, but never selects the issue").
2. **A published schema and atomic apply for instance files.** Warp publishes JSON Schema per file kind, a standalone validator, and a PR check. It applies a definition whole or keeps the last valid one. kinby already validates `package.yaml` through `PackageConfig` and checks packages before an update. Publishing those models as JSON Schema (`ROUTINE.md` frontmatter, `package.yaml`) would give editor completion and let `routine_write` and the hub reject a bad file before it replaces a good one.
3. **Opt-in retry for side effects, automatic only for the agent.** Archon's rule matches ADR 0029's Git rules: AI steps may retry transient errors, while `gh` mutations and pushes run once unless declared safe. If kinby ever makes stages declarative, retry belongs per stage with this default. Goose's `checks` + `on_failure` is the same shape as `checks.commands` with one repair attempt. kinby resumes the same client session for the repair (ADR 0045), where goose resets history. Keep kinby's choice: the repair needs the implementation context.
4. **Safe outputs for the model's last step.** gh-aw keeps the agent read-only and applies writes from structured output with per-type `max`. The coder routine's model step only comments a report. Running that turn read-only, with a `comment` output applied by the routine, would cap what an injected issue body can make it do. This is a small extension of "Treat the report as data".
5. **Deadlines on outside-event waits.** Archon's event wait must carry `deadline_ms` and expires instead of hanging. Babysitting already gets that from its hourly scan and `round_limit`. Keep GitHub as the state and the stateless re-entry: it survives restarts with no run store. If a future stage must wait inside one run (for CI, say), give the wait a deadline and an `expired` outcome rather than an open-ended pause.
6. **Separating agents from automations.** Warp keeps who runs (agent: harness, model, instructions, skills) apart from when it runs (automation: trigger, filter, prompt), and one agent can serve several automations. kinby's `package.yaml` sections (`implementation`, `review`, `babysitting`) are already agent definitions, and routines are automations. The borrowable part is the name: a named stage profile (`client`, `model`, `effort`, timeouts) that routines reference, instead of one section per routine.

Not worth borrowing:

- **Stage order as prose in a foreman prompt.** This is Warp's model, and ADR 0029 rejected it (D4) because a prompt cannot enforce limits, branches or labels.
- **A durable DAG engine with paused runs and resume caching** (Archon). It solves long in-run waits that kinby avoids by keeping state on GitHub. It would add a run store, a resume path and a signal API for nothing the coder needs today.
- **A compile step** (gh-aw). kinby reads `ROUTINE.md` and `package.yaml` at each run, so an edit takes effect on the next firing with no build.
- **Human gates as prompt policy.** Warp itself says the real gate is branch protection, and gh-aw puts its gate in GitHub Environments. kinby's merge gate is already GitHub's: the factory labels and never merges.
