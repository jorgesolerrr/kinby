Blueprint

Instance tools

Stamped at e0afd95: paths and symbols are true at this commit.

At a glance explanation

You ask your kinby for a routine or a skill in conversation and it installs the file, under the gate, in that turn. Seven core write tools, the instance tools, take whole ROUTINE.md and SKILL.md files, validate them with the loaders the scheduler and the skills catalogue already run, and replace the target directory in one rename. The decision that constrains the rest is that these are ordinary write tools under the existing presets: the user's permissions.toml and the thread's mode decide, and no second permission system appears.

Problem explanation

You ask your kinby to check the team calendar every morning and summarize it. The model knows the routine format from the write-routine skill, drafts a good ROUTINE.md, and stops. The workspace file tools in plugins/defaults/files.py resolve every path under the workspace and refuse anything outside it, so routines/ is unreachable. bash can reach it and asks in every mode below full-access, which makes a shell command the only door. You copy the draft into the directory by hand. The same wall stands in front of "turn that routine off for the week", "turn it back on", "delete it", and "save what we worked out as a skill". The README promises an agent that proposes routines itself. Today it proposes and cannot install.

Solution explanation

You say "every morning at nine, summarize my calendar". The model reads the write-routine skill, calls routine_write with the complete file, and the REPL shows you that file as an indented block and asks. You say yes. The file lands in routines/calendar/, the scheduler arms it on its next tick, and the model tells you when it fires next. "Turn it off" is routine_set_enabled, which flips one line and leaves the rest of your file untouched. "Turn it back on" after the failure policy disabled it is the same call, and it starts a fresh failure streak. "Delete it" refuses while deliveries are waiting for that routine and says how many. "Save that as a skill" is skill_write, and the result tells you when the new skill shadows a packaged one. Under full-access none of this asks, because that is what full-access means. I think the whole-file shape is the part that will age best: the model writes the file a person would write, and every future frontmatter key is a file matter, not a tool parameter.

Bird's-eye flow reference

One figure of the feature end to end for a routine write under ask. Boxes are functions and stores. Arrows carry the data that crosses. Decision ids lead the label where a decision picked the route.

  1. _call_tools builds a ToolCall for routine_write and hands it to evaluate with the policy, the thread's mode and the tool.
  2. Under ask, evaluate answers ASK with rule mode.ask.write. The runner interrupts with an ApprovalRequested carrying the whole file as an argument (D4).
  3. _answer_approval prints the arguments as a block, because one spans lines, and sends the answer back as an ApprovalDecision.
  4. On approve, the runner invokes routine_write with the arguments and the ToolContext (D1).
  5. routine_write stages ROUTINE.md and an optional run.py in a temporary directory and runs _load_routine on the staged copy (D5). A failure returns the loader's message and stops here.
  6. On success it renames the staged directory over routines/<name>/ (D5) and returns the result text with the next firing time (D14).
  7. The runner emits ToolCall, ToolGated and ToolResult to the event log, as for any tool.
  8. Scheduler.tick reads every routine file on its next pass and arms the new Routine.
  9. routine_history folds the log; a non-error ToolResult for routine_set_enabled resets that routine's failure count (D10), which the scheduler reads on the same tick.

Ground-level flows reference

One subsection per flow. Each has a sequence whose participants are the functions from the module map, then a numbered step list naming the data shape at each hop.

Flow: write a routine

  1. _call_tools calls evaluate: input GatePolicy, PermissionMode, ToolCall, Tool; output GateDecision(ASK, GateRule("mode.ask.write")). A tools.routine_write line in permissions.toml overrides this.
  2. The runner interrupts: input ApprovalRequested(approval_id, name, arguments, rule); the REPL receives it on the thread subscription.
  3. _answer_approval prints the block form because arguments["content"] spans lines (D4), reads the answer, and calls thread.approval.respond: input ThreadApprovalRespondCommand(thread_id, approval_id, answer).
  4. On approve, the runner calls Tool.ainvoke on routine_write: input arguments (name: str, content: str, code: str | None) and ToolContext(instance, thread_id).
  5. routine_write checks the name (D5), stages ROUTINE.md and, when given, run.py in a temporary directory beside routines/, copies an existing run.py when code is omitted, and calls load_routine_file on the staged copy: output Routine, or an exception with the loader's message.
  6. Valid: the staged directory replaces routines/<name>/ in one rename; output the result text with the next firing time in the instance zone and the signal path (D14).
  7. Invalid: output an error ToolResult with the loader's message; the target is untouched.
  8. The runner emits ToolGated(action, rule, decided_by=USER) and ToolResult(output, error) as for any tool.

Flow: enable after the failure policy

  1. After the gate and approval, the runner calls routine_set_enabled: input {name: str, enabled: bool} and ToolContext.
  2. The tool loads the routine by name, output Routine or a not-found error, and calls set_routine_enabled(routine, True), which rewrites only the enabled line and keeps the file's other bytes and line endings.
  3. Output the result text: the routine name, the next firing time when scheduled, and disabled when the call disabled it (D14).
  4. The runner emits ToolResult(call_id, name="routine_set_enabled", error=False); the earlier ToolCall carries the arguments.
  5. On its next pass, Scheduler.tick calls routine_history over every event.
  6. The fold remembers ToolCall events named routine_set_enabled with enabled true by call id, and on the matching non-error ToolResult sets that routine's failure_count to zero and drops its unhandled failures (D10). An error result resets nothing.
  7. Output RoutineHistories; _arm arms the enabled routine, and its next failure counts from one (D7).

Flow: delete with the queue checked

  1. After the gate and approval, the runner calls routine_delete: input {name: str} and ToolContext. A name with no directory is a not-found error result.
  2. The tool folds the event log with routine_history: output RoutineHistories, and reads RoutineHistory.pending for that name.
  3. No pending delivery: the tool removes routines/<name>/ with its run.py; output "Deleted routines/<name>/.". The scheduler drops the routine on its next pass.
  4. Pending deliveries: output an error ToolResult naming the count (D12); the directory is untouched. Disabling stays available, and the deliveries still fire.

Flow: write a skill

The same shape as the routine write with three differences, so it has no figure of its own. The staged file is skills/<name>/SKILL.md and the loader is load_skill_file. The tool refuses when the frontmatter name differs from the directory name (D11). The result names the packaged or workspace skill the new one shadows, found by loading the skill tiers the way load_skills does (D11, D14). skill_delete removes the directory and never touches a packaged or workspace skill.

Data shapes reference

The new module's surface and the existing types it reads or changes. No contract type changes; the manifest and its schema are untouched.

Every verb returns a string for the model. Arguments: name is a routine or skill name; content is the complete markdown file; code is the complete run.py text or absent; enabled is a boolean. The result strings are the D14 texts. No event, contract, manifest, or schema type changes.

Testing reference

Seams
The instance tools invoked with a ToolContext against a temporary instance, because every decision from D3 to D14 is visible in a file or a result string there. LangGraphRunner with a scripted model for the gate and approval path (D1, D4, D6). The routine history fold and the scheduler for the streak (D7, D10). run_repl for the rendering (D4). The packaged skill text (D13).
A good test here
Asserts the files in the instance directory, the events a subscriber sees, the string a tool returns, or the text the REPL prints. Never the staging directory, the rename call, the loader's internals, or the fold's bookkeeping.
Prior art
tests/test_memory_tools.py for core tools through the runner with a scripted model; tests/test_routines.py for routine files in a temporary instance and firings; tests/test_scheduler.py for the failure policy; tests/test_repl.py for approval prompts; tests/test_packaged_skills.py for the shipped skill.

Cases

  1. routine_write with a valid file creates routines/<name>/ROUTINE.md, the scheduler lists it armed, and the result carries the next firing time in the instance zone, flow write a routine, protects D3, D5, D14.
  2. An invalid cron, a missing description, a run.py defining two tools, and a name with a slash each return the loader's message and leave the directory as it was, flow write a routine, protects D5.
  3. A rewrite without code keeps the existing run.py; one with code replaces it, flow write a routine, protects D3.
  4. Under ask, a model call to routine_write raises an approval whose arguments carry the file; approve writes it and emits ToolGated and ToolResult; deny leaves the directory untouched; under full-access no approval appears, flow write a routine, protects D1, D4.
  5. Every verb is in the tool snapshot of a user turn and of a routine turn, flow all, protects D6.
  6. routine_set_enabled flips only the enabled line and preserves the rest of the file byte for byte, including line endings, flow enable, protects D3.
  7. A routine disabled at ten failures, enabled through an approved routine_set_enabled, fails once and stays enabled with a failure count of one; an errored enable result resets nothing, flow enable, protects D7, D10.
  8. routine_delete removes the directory when nothing is pending and refuses with the count when a delivery waits, flow delete, protects D12.
  9. skill_write refuses a frontmatter name that differs from the directory, reports the packaged skill it shadows, and the catalogue lists the new skill; skill_delete removes it, flow write a skill, protects D11, D14.
  10. An approval whose argument spans lines prints the block form; one whose arguments do not keeps the one-line form, flow write a routine, protects D4.
  11. The write-routine skill names routine_write and no longer names #61, flow write a routine, protects D13.

Out of scope reference

  • Agent-authored tools in tools/. Agent authors its own tools (#161) on the map.
  • A set_model verb or any write to kinby.toml. Ruled out of the v1 map.
  • Writes to permissions.toml, SYSTEM.md, RECAP.md, or the profile through instance tools.
  • History or revert for the instance directory. Fog on the map as "instance directory history".
  • A rendered diff on the approval event. Fog on the map as "approval previews".
  • Contract methods or CLI commands for creating and editing routines.
  • Excluding instance tools from routine or signal turns.
  • Workspace convention skills. The workspace file tools already reach them.

Open questions reference

Points the grilling did not settle. Each with the options on the table and the recommended default. The agent building this stops and asks before acting on any of them.

  1. The exact name rule. Options: letters, digits, hyphens and underscores starting with a letter or digit; any name that is a single path segment without a leading dot. Default: the first, so a name is always a valid signal path.
  2. What routine_list includes. Options: the RoutineSummary fields the contract already returns; name, description, schedule, enabled, mode, signal and pending count only. Default: the second, enough for the model to talk about state without turning the tool into routine.list.
  3. Whether routine_read also returns the next firing time. Options: file text only; file text plus the D14 facts. Default: file text only, since routine_list carries state.

Glossary reference

instance tool
A core write tool through which the agent changes its own instance, such as a routine or a skill, under the gate like any other write. Workspace file tools never reach the instance.
instance
One kinby deployment: a directory that owns its behavior configuration, memory and transcripts.
routine
A wake an instance owns: a prompt, and optionally the instance's own code step that runs first. Lives as a directory in the instance; its file is the source of truth.
code step
A routine's own deterministic code, a tool never offered to the model, that runs before the model.
skill
A markdown instruction set the model reads on demand, listed by name and description.
tool snapshot
The fixed, name-sorted set of tools for one turn.
gate
The check every tool call passes through before it runs: allow, ask, or deny from the tool's write flag and the instance's policy.
permission mode
A named preset of gate rules a thread runs under: read-only, ask, auto, or full-access.
approval
A user decision a live turn waits on before it continues. Requested as an event; answered through the contract.
failure policy
The rule that counts consecutive failed firings, reports the first failure, and disables a routine at ten failures.
delivery
One authenticated inbound call the receiver accepted for a routine, recorded at receipt and fired by the scheduler.
event
One sequence-numbered record in a thread's durable history.
