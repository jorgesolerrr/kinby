Blueprint

Signal receiver

Stamped at 63e8236: paths and symbols are true at this commit.

At a glance explanation

You get a routine that a webhook can wake: a signal block in ROUTINE.md, a [serve] listen address in kinby.toml, and kinby serve answering POST /signals/<routine> with a bearer or HMAC check. The receiver never starts a turn. It records each accepted call as a signal.received event on a fresh thread and answers 202, and the scheduler fires those deliveries oldest first when the instance is free, through the same wake path a cron firing uses. The decision that constrains the rest is that the event log is the delivery queue: a delivery that arrives during an hour-long firing or just before a crash waits in the log instead of being lost, which is what makes GitHub, a provider that never retries, a safe first source.

Problem explanation

Your kinby acts on a schedule now and on nothing else. When someone labels a GitHub issue ready-for-agent, the only way your agent notices is a routine that polls every few minutes and spends a turn each time to find nothing. Every provider that can push has to be polled. kinby serve opens no socket: _serve_instance in src/kinby/cli/main.py boots the runtime, starts the scheduler, prints the routine list and waits for a signal to stop. RoutineTrigger knows scheduled, manual and catch-up. Turns.wake takes an origin, and only Scheduler._fire calls it. The write-routine skill already calls a minutes-level poll on a source that can push a smell, and offers nothing else.

Solution explanation

You add a signal block to a routine and a [serve] listen line to the manifest, put the secret in the instance .env, and point the provider at /signals/<routine>. Each accepted call becomes a delivery on its own thread, answered 202 at once. When the instance is free the scheduler fires it as an ordinary routine turn: the code step runs first with the delivery as its signal argument and returns None for anything that needs no work, the prompt says the routine was woken by a signal, and the gate, recap, statistics, rating and failure policy apply unchanged. kinby routine run <name> --payload <file> fires the same path by hand with a saved delivery, so you test the GitHub routine before wiring the hook. kinby routine list shows the path, the auth scheme and how many deliveries are waiting.

Bird's-eye flow reference

One figure of the whole feature end to end. Boxes are modules or systems. Arrows carry the data or event that crosses. Decision ids lead the label where a decision picked the route.

Prose walkthrough, one step per arrow.

  1. The provider posts to /signals/<name>. The receiver resolves the routine, checks the body size and verifies the token or signature (D4, D5, D16).
  2. The receiver hands the delivery to Scheduler.receive, which creates the thread, fixes the turn id and appends signal.received to EventLog (D10, D21).
  3. The receiver answers 202 with the thread id and sequence. On a repeated delivery id it answers 200 with the existing thread (D17).
  4. Scheduler.tick folds the log through routine_history and finds the pending deliveries next to the due schedules (D23).
  5. When the instance is idle the scheduler calls Turns.wake on the delivery's thread with the routine prompt, the signal origin and the fixed turn id (D11).
  6. Turns appends turn.started with that turn id and spawns LangGraphRunner.run with the TurnRequest.
  7. The runner reads the delivery back from the thread and calls the code step with it as the signal argument. None closes the turn as no work; any other result becomes the data block under the signal cue (D6, D12, D15).

Ground-level flows reference

One subsection per flow named in the bird's-eye figure. Each has a sequence whose participants are the functions from the module map, then a numbered step list naming the data shape at each hop. A third figure draws the delivery lifecycle.

Flow: receive

  1. The provider posts to /signals/<name>: input raw bytes and headers. A body over one megabyte answers 413 here.
  2. The receiver calls load_routines and looks the routine up by name: output Routine with signal: SignalConfig. Unknown name or no signal block answers 404.
  3. The receiver verifies the call: input SignalConfig, headers, raw body; output a boolean from hmac.compare_digest. False answers 401 with an empty body. A disabled routine answers 410 after this check.
  4. Rejected: the status goes back, the process log gets path and reason, the event log gets nothing.
  5. Accepted: the receiver builds a Delivery (secrets stripped, keys lowercased, content type, body text, delivery id, received time) and calls Scheduler.receive with the signal trigger.
  6. Scheduler.receive folds all_events() through routine_history; a matching delivery id returns the existing thread and sequence, answered 200.
  7. Otherwise it creates the thread titled <name> · <delivery id or time>, fixes a turn id, and appends SignalReceived(delivery): output Event with its sequence.
  8. It nudges the worker with schedule() and returns AcceptedResult. The receiver answers 202 with the thread id and sequence.

Flow: fire

  1. Scheduler.tick folds all_events() through routine_history: output per routine a RoutineHistory with pending: list[PendingDelivery] next to the last run and failure count.
  2. It waits for the instance to be idle and picks the oldest ready work: a pending delivery by sequence or a due schedule by armed time.
  3. It calls Turns.wake on the delivery's thread: input the routine prompt, RoutineOrigin(name, trigger=SIGNAL, delivery=id), and the fixed turn id. The daily budget check and the busy rule apply as for any wake.
  4. Turns appends TurnStarted with that turn id, returns AcceptedResult, and spawns the runner with a TurnRequest.
  5. LangGraphRunner._prepare_turn loads the routine by name, reads the thread's events with stored(thread_id), and takes the Delivery from its signal.received event.
  6. With a code step, it calls ainvoke_raw with signal set to the delivery (body decoded when JSON) merged with the frontmatter arguments, under the routine's mode and the gate, as today.
  7. None: the turn closes as turn.completed with the no-work outcome and no model call.
  8. Text: render_wake frames it as [Routine: <name>, woken by a signal] plus the prompt and the data block, and the model runs. Without a code step the body text is the payload.

Testing reference

Seams
One new seam: the receiver over a real socket on an ephemeral port, in front of the dispatcher with a scripted runner and the scheduler on a fake clock (D2, D10, D16). Every other case reuses an existing seam: the scheduler on a fake clock, the LangGraph runner with a scripted chat model, the routine loader, the CLI through main, the REPL through run_repl, the manifest and schema, the packaged skill.
A good test here
Asserts what a caller or subscriber sees: the HTTP status and body, the events on the delivery's thread, the routine list result, the printed lines. Never the receiver's routing table, the scheduler's ready list, or the fold's private state.

  2. A wrong signature gets 401 with an empty body and no new thread, flow receive, protects D5, D25.
  3. A bearer routine accepts the right token and rejects a wrong one, flow receive, protects D22.
  4. An unknown path gets 404 with no secret read, flow receive, protects D4.
  5. A disabled routine gets 410 after auth and no record, flow receive, protects D14.
  6. A body over one megabyte gets 413, flow receive, protects D16.
  7. A repeated delivery id gets 200 with the existing thread and no second event, flow receive, protects D17.
  8. A routine whose secret variable is unset warns and is absent from the receiver's routes, flow receive, protects D5.
  9. After the scheduler drains, the delivery's thread has turn.started with the signal trigger, the delivery id and the same turn id as signal.received, flow fire, protects D11.
  10. A pending delivery and a due schedule fire oldest first, flow fire, protects D23.
  11. A log holding signal.received with no turn.started fires on the first pass after boot, flow fire, protects D10, D23.
  12. A delivery received while a routine turn runs waits and fires after it, flow fire, protects D10.
  13. A delivery for a routine disabled after receipt fires; one for a deleted routine fails as not found, flow lifecycle, protects D23.
  14. The code step receives signal with a decoded JSON body and the frontmatter arguments; None closes the turn as no work with no model call, flow fire, protects D6, D15.
  15. Without a code step, the model receives the body in the data block under [Routine: name, woken by a signal], flow fire, protects D12.
  16. A failed signal firing increments the failure count and the tenth disables the routine, flow lifecycle, protects D14.
  17. routine.run with a payload records a delivery with the manual trigger and fires it, and kinby routine run --payload streams the turn, flow fire, protects D13.
  18. routine.list carries path, auth scheme and pending count; the CLI table, the REPL startup line and the serve banner print them, flow fire, protects D24.
  19. The loader parses both schedule and signal on one routine, rejects HMAC without a signature header, and rejects a code step without a signal parameter, flow receive, protects D19, D15.

Out of scope reference

  • Provider adapters in core. Gmail push, Stripe's timestamped signature and any provider-specific parsing are recipes or instance code.
  • Destinations and a send tool. A silent successful firing stays with the destinations design on the map.
  • Workflows as a first-class concept. Fog on the map, first case the GitHub issue-to-PR loop.
  • Preemption of a running turn by a delivery. Deliveries wait in the log.
  • The RPC socket in front of the dispatcher. The server effort adds it to the [serve] server.
  • TLS, rate limiting and IP allowlists. A reverse proxy or tunnel owns them.
  • The agent writing a signal routine itself. Agent modifies its own instance (#61).
  • One-shot reminders. One-shot scheduling (#119).

Open questions reference

Points the grilling did not settle. The agent building this stops and asks before acting on any of them.

  1. Content type of a manual payload from --payload <file>. Options: infer application/json when the file parses as JSON and text/plain otherwise; a --content-type flag. Default: infer.
  2. Body of GET /health. Options: empty 200; JSON with the instance id. Default: JSON with the instance id.

Glossary reference

Signal
An inbound stimulus from outside the instance, such as a webhook call, that wakes the agent without a schedule.
Receiver
The part of serve mode that listens for signals, authenticates each call against the routine it names, and records the accepted ones as deliveries.
Delivery
One authenticated inbound call the receiver accepted for a routine, recorded the moment it arrives. The scheduler starts its turn when the instance is free.
Routine
A wake an instance owns: a prompt and optionally a code step, started by a schedule, by a delivery, or by hand.
Firing
One attempt to start a routine turn, whether scheduled, caught up, manual, or started by a delivery.
Code step
A routine's own deterministic tool that runs before the model and may report nothing new, completing the turn with no work.
No work
A completed turn whose code step found nothing for the model to do. Neither model runs.
Wake
The start of a turn by anything other than the user typing. Every wake carries an origin.
Origin
What started a turn: the user, a routine, or a signal.
Scheduler
The instance's coordinator of routine wakes, whether due by schedule or waiting as a delivery.
Serve mode
An instance runtime without a REPL, kept alive so the scheduler can fire routines and the receiver can listen.
Event
One sequence-numbered record in a thread's durable history. Never a synonym for signal.
