# Research: Graphiti/Neo4j Graph Memory in Practice

> Resolves wayfinder ticket 03. Goes one level below `research/landscape-lindy-and-personal-agents.md` §4. Facts checked against the [getzep/graphiti repo](https://github.com/getzep/graphiti), [Zep's Graphiti docs](https://help.getzep.com/graphiti/getting-started/quick-start), GitHub issues, and hands-on third-party reports. Researched 2026-08-10; library at v0.29.3 (2026-07-27).

## 1. Graphiti as a Python library

**Package/runtime.** `pip install graphiti-core` (Python ≥ 3.10, async-first — every API is `await`ed). Optional extras select providers/backends: `[anthropic]`, `[groq]`, `[google-genai]`, `[falkordb]`, `[falkordblite]`, `[neptune]` ([README](https://github.com/getzep/graphiti)). Telemetry is on by default, opt-out via `GRAPHITI_TELEMETRY_ENABLED=false`.

**Ingest API.** One central call ([quick start](https://help.getzep.com/graphiti/getting-started/quick-start)):

```python
graphiti = Graphiti(neo4j_uri, neo4j_user, neo4j_password)   # or with llm_client=, embedder=, cross_encoder=
await graphiti.build_indices_and_constraints()               # once, at setup

await graphiti.add_episode(
    name="...",
    episode_body="...",                       # str or JSON string
    source=EpisodeType.text | .message | .json,
    source_description="...",
    reference_time=datetime(...),             # event time -> bi-temporal t_valid
    group_id="user-123",                      # namespace / one graph per subject
)
```

Also: `add_episode_bulk()` (batch, skips some incremental resolution), `retrieve_episodes()` (recent episodes by time), `build_communities()` (Leiden-style community nodes for corpus-level summaries), and `add_triplet()` for injecting entity–edge–entity facts directly, bypassing LLM extraction — the relevant escape hatch when you already have structured facts (requested formally in [issue #1299](https://github.com/getzep/graphiti/issues/1299), where a user found LLM extraction "slow and costly" for pre-linked data).

**Ontology as Pydantic.** `add_episode` accepts `entity_types=` / `edge_types=` dicts of Pydantic `BaseModel` classes (all fields Optional, `Field(description=...)` drives extraction), plus `edge_type_map={("Person","Company"): ["Employment"], ...}` constraining which edges may connect which entity pairs, and `excluded_entity_types=[...]` ([custom types docs](https://help.getzep.com/graphiti/core-concepts/custom-entity-and-edge-types)). This is how you'd model `Person`, `Project`, `Preference`, `Tool` for a personal agent. Reserved attribute names: `uuid`, `name`, `group_id`, `labels`, `created_at`, `summary`, `attributes`, `name_embedding`.

**Retrieval API.** `await graphiti.search("query")` = hybrid edge (fact) search fusing cosine-similarity embeddings + BM25 fulltext, optionally reranked by graph distance from a `center_node_uuid` (personalize results around the "user" node — the key trick for a personal agent). Lower-level `graphiti._search(query, config=RECIPE)` takes preconfigured recipes (e.g. `NODE_HYBRID_SEARCH_RRF` for nodes instead of edges; RRF, MMR, and cross-encoder reranking variants exist). Retrieval makes **no LLM calls** by default (embedding call + DB queries only) — sub-second, typically 200–300 ms ([quick start](https://help.getzep.com/graphiti/getting-started/quick-start), [hands-on report](https://pub.towardsai.net/i-needed-memory-for-my-ai-agent-and-found-this-knowledge-graph-framework-55c94880820e)).

**LLM providers for internal extraction** ([LLM configuration](https://help.getzep.com/graphiti/configuration/llm-configuration)):

| Provider | Client | Notes |
|---|---|---|
| OpenAI | `OpenAIClient` (default) | native structured output; default path assumes `OPENAI_API_KEY` |
| Azure OpenAI | `OpenAIClient` + `AsyncAzureOpenAI` | must opt into v1 API |
| **Anthropic/Claude** | **`AnthropicClient`** (`graphiti-core[anthropic]`) | **fully supported.** `LLMConfig(api_key=..., model="claude-sonnet-4-...", small_model="claude-3-5-haiku-...")`. Docs flag it as lacking *native* structured-output mode (Graphiti coerces JSON via tool-use/prompting), but list Anthropic among the providers that "reliably honor" schemas. |
| Google Gemini | `GeminiClient` | native structured output |
| Groq | `GroqClient` | |
| Ollama / any OpenAI-compatible | `OpenAIGenericClient` | schema injected into prompt; unreliable with small models |

Two-tier model config: `model` (extraction) + `small_model` (cheap classification/dedup subcalls). **Gotcha for an Anthropic-only stack:** even with `AnthropicClient`, Graphiti still needs an embedder and a cross-encoder reranker — the docs state plainly: "When using Anthropic for LLM inference, you still need an OpenAI API key for embeddings and reranking functionality," unless you swap in Gemini/Voyage/local embedders explicitly. Anthropic ships no embedding API, so a second provider (or local model via Ollama's OpenAI-compatible endpoint, e.g. `nomic-embed-text` through `OpenAIEmbedderConfig(base_url=...)`) is unavoidable.

**Embedders:** `OpenAIEmbedder` (default), `GeminiEmbedder`, Voyage, Azure, or anything OpenAI-compatible/local. Embeddings are stored as node (`name_embedding`) and edge (`fact_embedding`) properties. **Warning:** the embedding model is baked into the graph — switching models later means re-embedding everything; pick once.

**Structured-output fragility is the #1 operational constraint.** Extraction/dedup depend on schema-conformant JSON; small local models "frequently emit non-conforming JSON" causing ingestion failures ([README](https://github.com/getzep/graphiti), [issue #868](https://github.com/getzep/graphiti/issues/868)). Use Sonnet-class or GPT-4.1-class for extraction, Haiku-class for `small_model`.

## 2. Neo4j footprint

**Schema created.** Three node labels — `Episodic` (raw episode `content`, `source`, `source_description`, `valid_at`, `created_at`), `Entity` (`name`, `summary`, `name_embedding`, dynamic extra labels from custom types, attributes), `Community` — and three relationship types: `(:Episodic)-[:MENTIONS]->(:Entity)`, `(:Entity)-[:RELATES_TO]->(:Entity)` (the fact edges, carrying `fact`, `fact_embedding`, `valid_at`/`invalid_at`, `created_at`/`expired_at` — the bi-temporal model), `(:Community)-[:HAS_MEMBER]->(:Entity)` ([architecture overview](https://deepwiki.com/getzep/graphiti/2-core-architecture)). `build_indices_and_constraints()` creates everything: range indexes on `uuid`, `group_id`, `created_at`, `valid_at`, `invalid_at`, `expired_at`; fulltext indexes on node names/summaries and edge facts. All multi-tenancy is by `group_id` property filtering, not separate databases.

**Community Edition suffices.** Requirement is Neo4j **5.26+** ([README](https://github.com/getzep/graphiti)); Graphiti uses plain Cypher, fulltext indexes, and vector similarity functions — all in CE. No APOC/GDS plugins required. CE limits that matter: one active database (fine — Graphiti defaults to `neo4j`; custom DB names since v0.17.0 mainly matter for Enterprise multi-DB), no RBAC, no hot backups (`neo4j-admin dump` offline or volume snapshots instead). For a single-user personal agent none of these bite.

**Docker resources.** Official image defaults to 512 MB heap + 512 MB page cache — deliberately small ([Docker config docs](https://neo4j.com/docs/operations-manual/current/docker/configuration/)). Neo4j's guidance: heap + pagecache + ~1 GB headroom < container limit; use `neo4j-admin server memory-recommendation --docker` for tuned values ([memrec tool](https://neo4j.com/docs/operations-manual/current/tools/neo4j-admin/neo4j-admin-memrec/)). For a personal-scale graph (tens of thousands of nodes), a **2 GB container (1 GB heap / 512 MB pagecache) is comfortable; 1 GB is the floor**. CPU is negligible at this scale — ingestion cost lives in the LLM calls, not the DB. Compose sketch: `neo4j:5.26-community`, env `NEO4J_server_memory_heap_max__size=1G`, `NEO4J_server_memory_pagecache_size=512M`, volume on `/data`.

**Alternative backends.** FalkorDB ≥ 1.1.2 (`[falkordb]`; Redis-module graph DB, much lighter — a few hundred MB — and there's `[falkordblite]` for an **embedded, no-server** variant on Python 3.12+, attractive for a zero-ops personal deployment); Amazon Neptune (needs OpenSearch Serverless for fulltext — irrelevant for self-hosting); **Kuzu is deprecated** ("upstream project no longer maintained", emits `DeprecationWarning`) ([README](https://github.com/getzep/graphiti)). Given the project leans Neo4j already, Neo4j CE in Compose is the mainline; FalkorDBLite is the fallback if the Neo4j container feels heavy.

## 3. What Graphiti does NOT cover — the hybrid layer's job

The cleanest evidence is Zep's own [Zep-vs-Graphiti page](https://help.getzep.com/zep-vs-graphiti): Zep (the commercial product) adds, on top of the Graphiti engine, **user/thread/session management, message persistence, context-block assembly, dashboards, access control, retention policies, and tuned extraction/reranking models**. Self-hosting raw Graphiti means building or skipping all of that. Concretely, for this project's memory architecture a hybrid layer must still provide:

- **Conversation transcripts / session model.** Episodes do store their raw `content` on `Episodic` nodes, so text is *recoverable*, but there is no conversation, thread, or turn abstraction, no pagination, no "give me the last session verbatim." Keep the canonical transcript in your own store (files or SQLite/Postgres) and feed Graphiti episodes as a *derived* stream — also lets you re-ingest if you change ontology or embedder.
- **Preference/profile store.** Graphiti has no first-class user profile; preferences become ordinary extracted facts ("Jorge prefers X"), which is probabilistic, non-inspectable, and ~$/latency-expensive to maintain. The landscape research's Lindy/Letta conclusion stands: keep a **human-legible plain-file profile** (`memory/profile.md`-style, injected each call) as the source of truth for preferences; use the graph for relational/temporal recall. You *can* nudge the graph with a custom `Preference` entity type, but don't make it the primary store.
- **Document storage.** Graphiti is not a document store or RAG chunk store; episodes should be conversation-turn-sized (long docs must be chunked by you, and users report degraded extraction on large episodes). Original files stay on disk / object storage.
- **Working memory & context assembly.** Nothing assembles a "memory context block" for the prompt — you write the glue that runs `search()` (+ `retrieve_episodes` for recency) and formats results.
- **Forgetting/curation UX.** Edge invalidation is automatic when contradicted, but there's no user-facing "view/edit/delete what you know about me" — a real gap versus Lindy's editable `.memory/` files; you'd have to build inspection UI over Cypher.
- **Ops:** backup, migration on ontology change, cost controls, ingestion queueing/retries (episode ingestion can fail mid-pipeline leaving partial subgraphs — see [issue #1021](https://github.com/getzep/graphiti/issues/1021)).

## 4. Alternatives if Graphiti disappoints

**cognee** ([cognee.ai](https://www.cognee.ai/), [benchmarks post](https://www.cognee.ai/blog/deep-dives/knowledge-graph-memory-benchmarks)). ECL (Extract–Cognify–Load) pipelines building a combined graph+vector layer, aimed at *corpus knowledge* (PDFs, Notion, Slack, images, audio) rather than conversational memory. Its big operational win is a **local-first default stack — SQLite + LanceDB + embedded Kuzu — no server database at all** ([Zep vs Cognee comparison](https://vectorize.io/articles/zep-vs-cognee)); its benchmarks show structured recall beating Mem0-style chunk recall on multi-hop questions. The trade-off: **no bi-temporal model and weak incremental semantics** — it re-cognifies datasets batch-style, so "what was true when," fact invalidation, and turn-by-turn evolution (the very reasons to pick a graph for an agent's memory) are missing; it would serve as the *document knowledge* layer, not the memory layer. Also note its default embedded-Kuzu backend rests on the now-unmaintained Kuzu project.

**Plain Neo4j + custom schema.** Hand-roll your own `(:Person)-[:PREFERS]->`, `(:Episode)-[:MENTIONS]->` schema with the [Neo4j Python driver](https://neo4j.com/docs/python-manual/current/), your own Claude extraction prompts, and Neo4j 5.x native vector + fulltext indexes. The trade-off is stark: **total control and one LLM call per episode of your own design (cheap, Claude-native, deterministic where you want it) versus rebuilding the genuinely hard parts** — entity resolution/dedup against the existing graph, contradiction detection and temporal edge invalidation, and tuned hybrid retrieval — which is precisely the multi-year R&D Graphiti embodies ([Zep paper arXiv:2501.13956](https://arxiv.org/abs/2501.13956)). Sensible only for a deliberately narrow schema (a dozen entity types about one user), where naive "match by name + embedding similarity" dedup may be good enough.

**neo4j-graphrag-python** ([PyPI](https://pypi.org/project/neo4j-graphrag/), v1.18.0, June 2026). Neo4j's first-party, well-maintained library: `SimpleKGPipeline` for entity/relation extraction from text/PDFs plus a strong retriever family (`VectorRetriever`, `HybridRetriever`, `VectorCypherRetriever`, `Text2CypherRetriever`), with **first-class Anthropic support** (also OpenAI, Vertex, Cohere, Mistral, Bedrock, Ollama) and sentence-transformers embeddings — notably it removes both of Graphiti's provider frictions (Claude for extraction, local embeddings). The trade-off: it is **batch, document-oriented GraphRAG with no temporal model, no episode/incremental-resolution machinery, and no memory semantics** — you'd get excellent Neo4j retrieval plumbing but write the entire "memory over time" layer (dedup-on-ingest, invalidation, recency) yourself. Best viewed as the toolkit for the *plain Neo4j* option above rather than a Graphiti peer.

## 5. Real-world reports and project health

**Maintenance health: strong.** 29.8k stars, ~3.0k forks, pushed the day of this research (2026-08-10), steady release cadence (v0.28.0 Feb-2026 → v0.29.3 Jul-2026), backed by a company (Zep) whose product runs on it — low abandonment risk ([GitHub API](https://api.github.com/repos/getzep/graphiti)). Counterweight: **471 open issues**, and commercial incentives mean the OSS library will stay the "engine without the platform" (§3).

**Issue themes** (recurring across the tracker):
- *Local/small-model structured-output failures* — the largest class: Ollama quickstart Pydantic validation errors ([#868](https://github.com/getzep/graphiti/issues/868)), `api_base` ignored → 401 against real OpenAI ([#1116](https://github.com/getzep/graphiti/issues/1116)), LiteLLM/non-standard-port setups ([#1023](https://github.com/getzep/graphiti/issues/1023)).
- *Anthropic-path rough edges*: MCP server + Anthropic 400 when `temperature=None` (an OpenAI-reasoning-model accommodation that broke other providers, [#1103](https://github.com/getzep/graphiti/issues/1103)); `group_id` kwarg crashing `AnthropicClient.generate_response` ([#1012](https://github.com/getzep/graphiti/issues/1012)). Anthropic is supported but is clearly the second-class-tested path; expect to pin versions and occasionally patch.
- *Cost/scale pushback*: users ingesting emails/transcripts at scale report "LLM costs become very expensive" and ask for extraction-free ingestion ([#1193](https://github.com/getzep/graphiti/issues/1193), [#1299](https://github.com/getzep/graphiti/issues/1299)); partial/incomplete graphs on interrupted ingestion ([#1021](https://github.com/getzep/graphiti/issues/1021)).

**Latency & cost per episode.** One episode triggers a *chain* of LLM calls — entity extraction → node dedup/resolution against the existing graph → edge extraction → per-edge resolution/invalidation → timestamp extraction → attribute/summary generation — plus embedding calls ([#1193](https://github.com/getzep/graphiti/issues/1193), [architecture](https://deepwiki.com/getzep/graphiti/2-core-architecture)). Observed numbers: **~5–20+ s wall-clock per conversational episode** (model-dependent; must run as a background task, never inline in the chat loop); throughput ~**50 episodes/min** at the default `SEMAPHORE_LIMIT=10`, tunable upward until the provider 429s ([README](https://github.com/getzep/graphiti)). One evaluator measured **600k+ tokens of LLM traffic per long conversation** ingested and P95 retrieval ≈ 300 ms, concluding it's fine for batch/scheduled workloads but a real cost for high-frequency pipelines ([Codex blog evaluation](https://codex.danielvaughan.com/2026/03/30/graphiti-agent-memory-store/)). Rough order of magnitude with a Sonnet/Haiku split: cents per episode; a chatty personal agent producing 50–200 episodes/day lands at **single-digit dollars/day of extraction spend** unless you route extraction to Haiku-only or local models (which then hit the structured-output wall). Query-side is cheap: hybrid search at 200–300 ms with ~10k nodes and no LLM calls ([Towards AI hands-on](https://pub.towardsai.net/i-needed-memory-for-my-ai-agent-and-found-this-knowledge-graph-framework-55c94880820e)).

**Personal-agent usage exists and works.** Multiple 2026 write-ups run exactly this stack — a personal assistant ingesting each conversational turn as an episode into Graphiti+Neo4j under Docker Compose ([Neural Maze](https://theneuralmaze.substack.com/p/building-agent-memory-with-knowledge)), LangGraph agents wired to the bundled **Graphiti MCP server** (episode add/search/delete over MCP — a fast integration path for a Claude Agent SDK app) ([Charles Chan](https://medium.com/@charlesmcchan/building-agentic-memory-with-langgraph-graphiti-via-mcp-bfab711c29eb), [MCP server README](https://raw.githubusercontent.com/getzep/graphiti/main/mcp_server/README.md)). Setup reports cluster around "operational in about an hour," with the pain arriving later in provider config and ingestion cost, not initial integration.

## Bottom line for the memory-architecture decision

Graphiti fits this project's shape: Python, async, Neo4j CE in Compose (2 GB container), Claude supported for extraction via `AnthropicClient` with a Haiku `small_model`. The two facts to design around: **(1) extraction cost/latency — every episode costs a multi-call LLM chain, so ingest asynchronously and consider ingesting distilled turns rather than every message; (2) Anthropic alone is insufficient — an embedding provider (OpenAI, Gemini, Voyage, or local via Ollama) is mandatory.** And Graphiti is only the relational/temporal recall layer: transcripts, the editable preference file, and document storage remain the hybrid layer's job, exactly as the landscape research's Lindy-style plain-file conclusion anticipated.
