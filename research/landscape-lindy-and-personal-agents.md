# Research: Lindy "AI Teammate" + Open-Source Personal-Agent Landscape

> Produced during wayfinder charting, 2026-08-10. Informs the destination and several tickets.

## 1. Lindy Teammate: what it is and how users interact with it

Lindy ([lindy.ai](https://www.lindy.ai/)) recently repositioned from a visual agent-builder platform into "Lindy Teammate," announced by founder Flo Crivello as "we kill the AI agent and introduce the AI employee" ([X announcement](https://x.com/Altimor/status/2086861887611019623), [Digg coverage](https://digg.com/tech/kvjs9acw)). Concrete facts:

**Channels.** Slack-native is the flagship: every employee gets a private assistant in their Slack DMs, and the whole team shares one in channels — "Ask in any channel, and Lindy responds in thread with an answer," with cited sources. Also: Gmail (drafts/schedules/replies in-inbox), iMessage/SMS, a web app, a Chrome extension, and it joins Meet/Zoom/Teams calls as a named participant ([lindy.ai](https://www.lindy.ai/), [assistant launch post](https://www.lindy.ai/blog/lindy-assistant-launch)). Slash commands manage the Slack connection ([docs](https://docs.lindy.ai/coming-soon/slack-commands.md)).

**"Behaves like a teammate" concretely.** (a) It completes work rather than drafting suggestions — marketing examples: "Updates HubSpot, writes the Notion doc, posts to #customer-success, books the kickoff, sends the welcome email." (b) It answers with sources from company data. (c) Proactivity is implemented as **routines** attached to the assistant — the docs are explicit that "It isn't a separate bot, it's automation attached to your Lindy, which is what makes Lindy proactive." (d) Background/async work: "Lindy constantly works its magic in the background... then starts anticipating what you need before you ask" — e.g., inbox triage before you wake, meeting prep assembled from email+calendar, follow-ups after calls. (e) Cross-session continuity: no re-instruction needed for recurring tasks; it "keeps learning, and becomes the self-updating brain of the whole business." One-off delegated work is covered under "ad-hoc tasks" ([docs](https://docs.lindy.ai/features/ad-hoc-tasks.md)). Zero-setup was a highlighted selling point in launch reception.

**Under the hood** the older architecture persists: Lindy (orchestrator) → Agents → Workflows → Steps, with six step types (Triggers, Actions, autonomous Agent Steps, Integrations, Conditions, Looping) ([docs intro](https://docs.lindy.ai/fundamentals/lindy-101/introduction), full index at [docs.lindy.ai/llms.txt](https://docs.lindy.ai/llms.txt)). The Teammate layer sits on top of this.

## 2. Lindy's memory, integrations, routines, and skills

**Memory = plain, versioned files.** This is the most architecturally interesting fact. Memory lives in a `.memory/` folder and skills in `.skills/` in a versioned file system surfaced on a "Files" page — "Think of it as Lindy's hard drive that you can see into" ([files docs](https://docs.lindy.ai/coming-soon/files.md)). The homepage: "Lindy learns everything about you, and it all lives in plain files. Open the memory folder, read what it remembers, and change it like a doc" (example memory: "Flo prefers charts over tables"). Three scopes: **Personal** (private per workspace), **Team** (workspace-wide, admin-edited, member-readable), **System** (global, read-only); Personal overrides Team overrides System. Every save creates a version; deleted files keep history for rollback. In the legacy agent builder, memories are "injected into the prompt for every LLM call" and editable by the agent via Memory actions ([agent settings](https://www.lindy.ai/academy-lessons/lindy-level-settings)). Agents are memory-aware of their own past actions (meetings booked, emails sent) and use that in decisions.

**Integrations.** Core connectors (Gmail, Slack, Notion, HubSpot, GitHub, Stripe, Salesforce, Calendly, Airtable, Google Drive) plus "1,000+ more," and **MCP support** ("Supports MCP, so the world is your oyster"). **Autopilot** gives agents their own cloud computer (browser/computer use) to escape API-integration limits. Compliance: SOC 2 Type II, GDPR, HIPAA ([integrations overview](https://docs.lindy.ai/integrations/overview.md)).

**Routines** (the recurring-automation primitive, [routines docs](https://docs.lindy.ai/coming-soon/routines.md)): a routine = **trigger + plain-English prompt + destination**. Created four ways: natural-language box ("Every weekday at 9, summarize my unread email"), conversationally in chat, one-click templates from a Discover library, or manual advanced settings. Triggers: time schedules (daily/weekly/monthly) or events (email received/sent, Slack message, calendar event, meeting end), narrowed by plain-English "Smart Filters" to avoid spurious runs. Destinations: chat, Slack DM, Slack channel/thread, SMS. Managed conversationally ("Change my morning routine to 9am", "Pause my follow-up bumps").

**Skills** ([skills docs](https://docs.lindy.ai/coming-soon/skills.md)): named reusable playbooks — each is a folder with a `SKILL.md` (metadata + instructions), a design conspicuously convergent with Anthropic's Agent Skills. Created by describing a procedure in chat (auto-saved as skill) or via a Skills page. Crucially for context economy, **Lindy sees only skill names + descriptions and pulls full instructions on demand when relevant** (progressive disclosure). Three tiers: personal / team-shared / built-in library (~40+: research, data analysis, decks, dashboards). "Do something once, save it as a skill, and your whole team gets it." Docs stress writing precise descriptions (they drive skill selection) and disabling rather than deleting.

## 3. Comparable open-source personal-agent projects

**OpenHands** ([github.com/OpenHands/OpenHands](https://github.com/OpenHands/OpenHands), [SDK paper](https://arxiv.org/pdf/2511.03690)) — Software-engineering agent, but its platform architecture generalizes. Tiny core: a **stateless Agent** that emits Actions; a **Conversation** loop persisting an **append-only EventLog** (event-sourced state with deterministic replay); a **Workspace** (local process or Docker) executing actions and returning Observations; LLM access via LiteLLM. The event stream *is* the memory and the integration point for auxiliary services. The V1 SDK formalizes nine components including Context Window Management (built-in condensation/summarization of the event log), a typed tool system with MCP, secrets registry, and security/confirmation gates. Interfaces: CLI, web GUI ("Agent Canvas"), cloud, SDK ([events docs](https://docs.openhands.dev/sdk/arch/events)). No first-class personal routines — it's task-invocation-oriented; scheduling comes from external triggers (e.g., GitHub events/CI).

**Letta (MemGPT)** ([letta.com](https://www.letta.com/blog/agent-memory/), [memory blocks](https://www.letta.com/blog/memory-blocks/)) — Agent server built on the MemGPT idea: treat the context window like OS main memory. **Core memory** = labeled, character-limited, agent-editable "memory blocks" pinned in the prompt (RAM); **archival memory** = vector DB searched on demand; **recall memory** = full message history on disk. Agents edit their own memory via tools. Two standout patterns: memory blocks are **shareable across agents**, and **sleep-time agents** ([docs](https://docs.letta.com/guides/agents/architectures/sleeptime/), [blog](https://www.letta.com/blog/sleep-time-compute/)) — background agents sharing the primary agent's memory blocks that reorganize/distill memory asynchronously during downtime, separating "memory shaping" from user interaction. Interface: REST API + ADE (web IDE); it's a framework, not a consumer assistant, so routines are up to the host application.

**Khoj** ([github.com/khoj-ai/khoj](https://github.com/khoj-ai/khoj)) — Self-hostable "AI second brain." Client-server: FastAPI/Django backend, **PostgreSQL + pgvector** for semantic search over personal docs (Markdown, org-mode, PDFs, Notion), clients for web, desktop, **Obsidian, Emacs**, and WhatsApp. Model-agnostic (local llama/qwen or hosted GPT/Claude/Gemini). Custom agents = persona + custom knowledge subset + chat model + tool permissions. **Automations** are its routines equivalent: natural-language scheduled tasks (effectively cron + saved query) that run server-side and deliver results by email/notification — e.g., a daily 8am Hacker News digest — explicitly turning it "from a reactive tool into a proactive assistant" ([overview](https://deepwiki.com/khoj-ai/khoj)). Memory is retrieval over the indexed corpus rather than an evolving learned profile.

**LangGraph ambient agents / executive email assistant** ([blog](https://www.langchain.com/blog/introducing-ambient-agents), [agents-from-scratch](https://github.com/langchain-ai/agents-from-scratch)) — A pattern more than a product: agents triggered by event streams rather than chat, running many concurrently, contacting the human only at defined points. LangGraph supplies the substrate: durable checkpointed graph state (agents pause indefinitely and resume), **built-in long-term memory as a namespaced key-value store with semantic search**, and **platform cron jobs** for scheduled polling (e.g., check inbox every N minutes). Codifies three human-in-the-loop primitives worth stealing: **notify** (flag, don't act), **question** (unblock the agent), **review** (approve before acting). Reference implementation: open-source executive email assistant with an "Agent Inbox" UI for pending approvals.

**Huginn** ([github.com/huginn/huginn](https://github.com/huginn/huginn)) — The pre-LLM ancestor (Ruby on Rails, since 2013). "Agents" are typed nodes (WebsiteAgent, RSS, IMAP, TriggerAgent, EmailAgent, webhook, JS agents) wired into a directed graph; they emit and consume **Events** stored in the DB, with cron-style `schedule` per agent and Liquid templating to transform payloads. Memory is just per-agent persisted state + retained event history — no semantics. Its lasting lesson is the **event-graph model for routines**: every automation is "trigger agent → transform agents → notification agent," inspectable and replayable. (n8n and Node-RED are its modern descendants.)

## 4. Best practices: graph memory and context management

**Graph-based agent memory — who does what:**
- **Zep/Graphiti** ([arXiv:2501.13956](https://arxiv.org/abs/2501.13956), [Neo4j write-up](https://neo4j.com/blog/developer/graphiti-knowledge-graph-memory/)): the strongest published architecture. A **temporally-aware KG** ingesting "episodes" (messages, business data) incrementally in real time; entities/relations extracted per episode and immediately resolved against existing nodes (no batch recompute). **Bi-temporal model**: every edge carries when the fact occurred *and* when it was ingested, with explicit `t_valid`/`t_invalid` intervals — so facts are invalidated, not deleted, enabling "what was true when" reasoning. Hierarchical subgraphs (episode → semantic entity → community). Retrieval fuses semantic embedding + BM25 + graph traversal. Beat MemGPT on Deep Memory Retrieval.
- **Cognee** ([cognee.ai](https://www.cognee.ai/blog/deep-dives/knowledge-graph-memory-benchmarks)): "ECL" (Extract–Cognify–Load) pipelines building a combined graph+vector store over document corpora; positioned as RAG replacement for the knowledge layer rather than conversational memory.
- **mem0**: vector-first extraction of discrete facts keyed to user/session/project; notably its own paper found the **graph variant lost** on single- and multi-hop recall while running ~3x slower at ~2x token cost, and they dropped it ([comparison](https://vectorize.io/articles/mem0-vs-zep), [analysis](https://codepointer.substack.com/p/agent-memory-systems-and-knowledge)).
- **Emerging consensus** ([survey](https://codepointer.substack.com/p/agent-memory-systems-and-knowledge)): graphs earn their cost only for **multi-hop questions and temporal/history reasoning**, where structured recall beats chunk recall by a wide margin; for simple preference recall, flat vector/file memory is cheaper and at least as accurate. A pragmatic hybrid: document/knowledge graph (Cognee/Graphiti-style) for the corpus + lightweight fact store (mem0/Letta-blocks/Lindy-style plain files) for runtime personalization. Note Lindy — a shipped product — chose **human-legible plain files** over a graph: inspectability and user editability were prioritized. Graphiti's bi-temporal edge-invalidation model is the design to copy if you go graph.

**Context-window management in long-running agents** ([Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools), [Arize overview](https://arize.com/blog/context-management-in-agent-harnesses/)):
1. **Compaction**: summarize and re-seed a fresh context before the window fills — proactively (thresholds well below the limit), preserving decisions/open questions, discarding stale tool output. Anthropic now ships a production compaction API (`compact-2026-01-12`).
2. **Structured note-taking / external memory**: persist state as files outside the window (progress notes, todo files); pair compaction with git commits so the agent can reconstruct state via `git log`/`git diff` after a reset. Lindy's `.memory/` folder and Letta's memory blocks are two productionizations of this.
3. **Sub-agent isolation**: a coordinator holds the plan; sub-agents burn tens of thousands of tokens exploring but return only 1–2k-token distilled summaries.
4. **Just-in-time loading / progressive disclosure**: keep lightweight identifiers (names + descriptions) in context and fetch full content on demand — exactly how Lindy loads skills and how deferred tools work generally.
5. **Tool-result clearing**: drop or truncate old tool outputs, keeping only conclusions.

**Design takeaways for a new open-source personal agent**: chat-DM as primary surface; routines as trigger(cron|event)+prompt+destination created in natural language; memory as user-inspectable versioned plain files with scoping, optionally backed by a bi-temporal graph for multi-hop recall; skills as SKILL.md folders selected by description with lazy loading; MCP for integration breadth plus browser/computer-use as escape hatch; LangGraph-style notify/question/review as the human-in-the-loop vocabulary; event-sourced append-only logs (OpenHands) for replayability; and a sleep-time background agent (Letta) for asynchronous memory consolidation.
